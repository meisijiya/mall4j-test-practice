1. 一句话回顾（第 3 课关键点）

第 3 课讲了三件事：

  1. 模块边界：yami-shop-api（用户端 :8086）服务小程序/H5/uni-app，yami-shop-admin（管理端 :8085）服务 mall4v，前后端通过 /sys/menu/nav 动态加载菜单路由。
  2. 可测点：每个模块至少挑出 3 个可测点，对应到等价类 / 边界值 / 场景法 / 状态迁移中的至少一种方法。
  3. 第一份接口用例：登录 → 加购 → 下单 → 支付，用 Postman / Knife4j 跑通最小闭环。
本课承诺
把"五种测试设计方法"打透成"输入 / 适用场景 / mall4j 案例 / 示例"四件套；再把 feature_list.json 里 D2+D3 的 150 条用例（90 + 60）按方法落到一张拆解比例表上——第 5 课直接进入测试开发全流程。

2. 五种测试设计方法速查

来源：D:/26测试/2026AI+软件测试第一篇课件/func-day01~day03 + ISTQB CTFL Syllabus v4.0 测试设计技术章节。术语统一：

#方法核心思想适用场景mall4j 落点
1等价类划分把输入域切成若干等价类，从每类挑 1 个代表输入字段取值多、枚举型字段登录账号、支付渠道、订单状态枚举
2边界值分析在等价类边界取上点 / 离点 / 内点数值范围、长度、阈值库存阈值、订单超时 30 分钟、自动收货 15 天
3场景法基本流 + 备选流，模拟用户从进入到完成业务流程、跨模块联动加购 → 确认订单 → 提交订单 → 支付 → 发货
4状态迁移画状态机，按迁移路径生成用例有限状态机、回调幂等订单 6 状态（UNPAY/PADYED/CONSIGNMENT/CONFIRM/SUCCESS/CLOSE）
5正交实验因子 × 水平的组合降维，用 Lₙ 表挑选代表多条件组合爆炸、配置矩阵角色 × 菜单 × 数据权限的组合
面试官的一句话
"等价类切输入、边界值取上下、场景法连流、状态迁移画机、正交实验降维"——五种方法不是并列清单，而是从"输入"到"流程"到"组合"的递进关系。

3. 等价类划分法（输入域切分）

来源：2026AI+软件测试第一篇课件/func-day01金融web项目/ 等价类章节。

三步法：① 划分等价类（有效 / 无效）② 为每个等价类编号 ③ 从每类至少挑 1 个代表用例。

mall4j 案例——登录用户名（来源：yami-shop-security 登录拦截器）：

输入条件有效等价类无效等价类
用户名长度4 ≤ len ≤ 20（字母数字下划线）len < 4；len > 20；含特殊字符；全空格；含中文
用户名存在DB 中已存在DB 中不存在
用户名是否启用status = 1status = 0（禁用）
示例用例
输入 "user01"（有效类）→ 期望进入密码校验；输入 "us"（无效类-长度过短）→ 期望返回"用户名长度 4-20"。

常见坑：等价类划分时把"数字字符"和"字母字符"分得太细，导致用例数膨胀。原则是"按业务规则切，不是按字符切"——同一个业务约束下的所有取值归为 1 类。

4. 边界值分析法（off-by-one）

来源：2026最新AI测试基础一套通关/1、AI测试基础/day02测试设计/ 边界值章节。

三点法：上点（边界值本身）、离点（距上点 1 个单位的值）、内点（区间内任意值）。每个边界条件至少取 3 个点。

mall4j 案例——订单自动取消 30 分钟阈值（来源：yami-shop-admin/.../task/OrderTask.java）：

边界条件上点离点（上）离点（下）期望
update_time = now − 30 分钟30:0029:5930:0130:00 触发取消；29:59 不触发；30:01 已触发
自动收货 15 天阈值15d 00:0014d 23:59:5915d 00:00:0115 天整触发；之前不触发
库存扣减阈值stocks = 1stocks = 0stocks = 21 扣成功；0 抛"库存不足"；2 扣后剩 1
测开金句
边界值要测"刚刚到达"和"刚刚没到"两侧——这是程序员写 < 与 <= 时最容易出错的地方。

注意：开源版的 30 分钟 / 15 天阈值在 OrderTask.java 里硬编码，没暴露到配置文件——二开抽阈值时，边界用例要重跑一遍。

5. 场景法（基本流 + 备选流）

来源：2026AI+软件测试第一篇课件/func-day02金融Web项目/ 场景法章节。

画法：从用户进入系统到离开画一条基本流（happy path），每个分支画备选流（error path / alternate path）。用 Mermaid / Visio 画流程图，再把每条路径翻译成用例。

mall4j 案例——加购 → 支付成功：

基本流：登录 → 加购(库存足) → 确认订单 → 提交订单 → 支付 → 发货 → 确认收货 → 评价
备选流 A：加购时库存不足 → 提示"库存不足"并阻止提交
备选流 B：提交时未选地址 → 提示"请先选择收货地址"
备选流 C：支付失败（余额不足 / 网关超时） → 订单保持 UNPAY，等待重试
备选流 D：30 分钟未支付 → OrderTask 自动取消，还原库存
备选流 E：支付成功 → 商家 24h 未发货 → 触发用户申请退款

用例计数规则：基本流 1 条 + 每条备选流 1 条 + 备选流之间组合（按需）。简单场景 5-8 条用例，复杂主链路 12-20 条。

面试答法
场景法不是"列举所有 if 分支"，而是"站在用户视角画完整旅程"——主链路 1 条 + 5 个典型备选流就够覆盖 80% 业务路径。

6. 状态迁移法（前置 → 触发 → 迁移）

来源：第 2 课的 9 行状态迁移表 + ISTQB CTFL 状态转移测试章节。

画法：① 列出所有状态 ② 列出每个状态能去往的状态 ③ 标注触发事件 / 触发方 / 副作用。每个迁移生成至少 3 条用例：正常路径、异常前置（非法前置状态）、幂等路径（重复触发）。

mall4j 案例——订单状态机核心 4 迁移（来源：OrderStatus.java）：

迁移正常路径异常前置幂等路径
1 → 2（UNPAY → PADYED）正常支付成功已发货订单再次调支付同一笔重复回调
2 → 3（PADYED → CONSIGNMENT）商家发货待付款订单发货同一订单重复发货
3 → 4（CONSIGNMENT → CONFIRM）用户确认收货待发货订单确认收货重复点击确认收货
3 → 5（CONSIGNMENT → SUCCESS）15 天自动收货14 天 23 时触发任务并发重复执行
测开用法
状态迁移用例数 ≈ 迁移数 × 3（正常 / 异常 / 幂等）。订单 9 个迁移 = 27 条用例；退款子表再单独走 5-8 条。

7. 正交实验法（因子 × 水平组合降维）

来源：2026最新AI测试基础一套通关/1、AI测试基础/day02测试设计/ 正交实验章节。

核心思想：当组合数为 因子数⁽¹⁾^水平数 时（全组合爆炸），用正交表 Lₙ(m^k) 挑选 n 行代表，使每对因子的每个水平组合都恰好出现 1 次。

mall4j 案例——角色 × 菜单 × 数据权限组合（来源：yami-shop-sys 权限模块）：

因子 / 水平水平 1水平 2水平 3
角色超级管理员运营客服
菜单订单管理商品管理会员管理
数据权限全部本店本人

全组合 = 3 × 3 × 3 = 27 条；用 L₉(3³) 正交表只需 9 条用例：

L9(3^3) 正交表
#  角色        菜单         数据权限
1  超管        订单         全部
2  超管        商品         本店
3  超管        会员         本人
4  运营        订单         本店
5  运营        商品         本人
6  运营        会员         全部
7  客服        订单         本人
8  客服        商品         全部
9  客服        会员         本店
简历金句
"用 L₉(3³) 正交表把 27 组合降维到 9 条用例，覆盖 3 角色 × 3 菜单 × 3 数据权限的全部交互"——这句直接写进 M1 项目经验。

工具：allpairs（Windows 命令行）自动生成正交表；mall4j 权限模块 4 因子 × 3 水平 = L₉(3⁴)，写到 D7 pytest 用例。

8. 150 条用例拆解比例表（D2 + D3）

来源：feature_list.json D2 + D3 行 + 第 2 课订单状态机表 + 本课五种方法。

拆解规则：每个模块按"业务复杂度 + 接口字段数"分配用例数，每条用例至少落一种方法。

模块用例数等价类边界值场景法状态迁移正交覆盖深度
登录 / 注册（D2）4015108—7（L₉ 选 7 条核心）字段级 + 流程级
商品 / SKU（D2）301286—4（规格 × 分类）多规格 + 库存
购物车（D2）20648—2（店铺 × 优惠）缓存一致性
订单 / 支付（D3）2554412（9 迁移 × 1 + 3 异常）—状态机 + 回调幂等
会员 / 权限（D3）15532—5（角色 × 菜单）Sa-Token 鉴权
兼容性 / 异常（D3）20864—2（端 × 网络）三端 + 网络异常
合计15051（34%）35（23%）32（21%）12（8%）20（13%）—
拆解原则
① 每个模块至少 2 种方法叠加（不能 100% 等价类）；② 状态迁移法留给订单 / 支付；③ 正交实验只用于 ≥ 3 因子的组合。

关键发现：等价类 34% + 边界值 23% = 57% 字段级覆盖；场景法 21% + 状态迁移 8% = 29% 流程级覆盖；正交 13% 组合覆盖——三者分层，互不重叠。

9. 用例评审 Checklist

来源：2026最新AI测试基础一套通关/1、AI测试基础/day03测试执行/ 用例评审章节 + qa-manual-istqb skill 评审模板。

评审维度（10 条 Checklist）：

  1. 覆盖完整性：每个需求点至少有 1 条用例（无遗漏）；每条需求点对应到至少 1 种方法。
  2. 边界就位：每个数值字段都有上点 / 离点 / 内点；时间阈值有"刚刚到 / 刚刚没到"两侧。
  3. 异常路径：每个基本流配 2-3 条备选流（异常 / 取消 / 超时）；不是 0 备选流。
  4. 幂等覆盖：支付 / 提交 / 确认收货等"按按钮"操作，至少 1 条重复触发用例。
  5. 状态机完整：每个迁移有正常 / 异常前置 / 幂等 3 条；非法前置状态被显式拒绝。
  6. 可执行性：前置条件 / 测试数据 / 预期结果三件套齐全；不是"测一下登录能不能成功"这种含糊描述。
  7. 数据驱动：同类用例用 YAML / Excel 参数化，避免重复；YAML 字段命名清晰。
  8. 优先级：P0（核心交易） / P1（重要流程） / P2（边界 / 异常）三级，P0 必须 100% 通过。
  9. 可追溯：每条用例标注来源需求编号 / 文档章节（如 doc/6-核心业务/6-支付流程.md §3）；删除需求时同步删除用例。
  10. 评审结论：通过 / 有条件通过 / 不通过 三档；不通过要列具体修改项 + 责任人。
M1 评审场景
D2 评审会上把这 10 条 Checklist 当成评分表——每条用例过一遍，未覆盖的当场补用例。150 条用例 × 10 维度 = 1500 个检查点，半天就能跑完一轮。

反模式：用例只写"输入 + 期望"，不写"前置条件"——执行时数据准备不出来，整条用例作废。
