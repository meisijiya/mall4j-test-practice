2. 为什么从 Postman 进阶到 pytest

Postman 不是不好——它是探索工具，不够 工程。pytest + requests 把"接口用例"升级成"接口测试工程"，4 个理由：

#理由Postman 局限pytest 优势本课落地
1 自动化 / CI Runner 需人工点；Newman CLI 可接入 CI 但断言用 JS bash run.sh 一键跑；GitHub Actions 用 pytest 步骤 run.sh 4 行：装依赖 → collect → 跑
2 IDE 友好 Postman Desktop 内存大；无断点 / 调试器 PyCharm / VS Code 完整断点、变量检查、Refactor common/base_api.py 173 行可单步调试
3 数据驱动 Runner 数据文件格式受限；CSV / JSON 转换链长 pytest.mark.parametrize + YAML 数据文件（pytest_yaml_cases） data/login_data.yaml 5 条参数化登录
4 与 Newman 互补 Postman / Newman 强在"接口链路演示" pytest 强在"用例逻辑 + 报告 + CI" M1-D4 演示 + M2-D6 回归 = 完整测试工程

MISSION.md 主线（第 9 段"用户目标"）：用户在秋招投递测试开发岗时，"pytest + requests 自动化起步"是必填项——不是会用 pytest 写 hello world，而是能交付一套 23 文件的工程骨架（入口 + fixture + common + api + testcases + data + reports），CI 接入即用。

简历金句
"基于 pytest + requests 设计 mall4j 接口自动化框架，覆盖登录 / 商品 / SKU / 订单 5+3+2 共 10 条 smoke + P1 用例，支持 session 级 token 复用 + YAML 数据驱动 + allure 优雅降级"——这句直接写进 M2 项目经验。

4. 核心概念 × 5（ApiClient 鉴权 / pluggy 陷阱 / fixture scope / allure 降级 / skip 兜底）

4.1 概念 1：ApiClient 自动鉴权 + ts/nonce 注入

common/base_api.py:147-165 提供 4 个便捷方法（get / post / put / delete），全部走 _request() 内部；_request 负责：

  • URL 拼接：f"{self.base_url}/{path.lstrip('/')}"
  • ts + nonce 自动注入 query（与 Postman prerequest 一致）
  • Authorization 自动注入 header（need_auth=True 且 self._token 非空时）
  • 统一 [REQ] / [RESP] / [BIZ] 日志

登录 + 加购的 sequence 流程：

sequenceDiagram

    participant C as ApiClient
    participant S as mall4j 后端
    U->>C: login(user, pwd)
    C->>C: 自动注入 ts / nonce query
    C->>S: POST /login + ts + nonce
    S-->>C: {code:200, data:{accessToken:"xxx"}}
    C->>C: set_token(token)
    U->>C: add_cart(prodId)
    C->>C: 自动注入 Authorization: Bearer xxx
    C->>S: POST /p/shopCart + Authorization + ts + nonce

代码片段（base_api.py 摘）：

def set_token(self, token: str) -> None:
    """注入 Sa-Token；之后所有 need_auth=True 请求自动带 Authorization。"""
    self._token = token

def post(self, path: str, *, need_auth: bool = True, **kw) -> requests.Response:
    if "json" in kw and "json_body" not in kw:
        kw["json_body"] = kw.pop("json")
    return self._request("POST", path, need_auth=need_auth, **kw)
设计要点
ApiClient 一个实例承载一个 session（连接复用）；__init__ 不发任何请求；业务码 ≠ 200 仅打 warn 不抛错——让用例自己决定 assert 行为，保留负向场景自由度（密码错 / 用户不存在等）。

4.2 概念 2：yaml 数据驱动 + pluggy 陷阱

pluggy.PluginValidationError 陷阱：pytest 把 conftest.py 当成 plugin 入口；顶层的 def pytest_yaml_cases(path, key) 会被 pluggy 当成 hook 函数校验签名——若签名不像 hook 就抛 PluginValidationError。

修法：helper 函数迁出 conftest.py，放进 common/data_loader.py，由测试文件 from common.data_loader import pytest_yaml_cases 显式导入。

# conftest.py 顶部注释（原文）
# yaml 数据驱动 helper 已迁出至 common.data_loader，避免被 pytest 当成 plugin hook 注册

# common/data_loader.py（按上下文推导）
def pytest_yaml_cases(path: str, key: str):
    """读 YAML 数据文件的 key 列表，用于 parametrize。"""
    import yaml
    with open(path, encoding="utf-8") as f:
        data = yaml.safe_load(f)
    return data[key]

# testcases/test_login.py 用法
@pytest.mark.parametrize("case", pytest_yaml_cases("data/login_data.yaml", "login_cases"))
def test_login(self, case, api_client, logger):
    payload = {"userName": case["userName"], "passWord": case["passWord"]}

反向教训：最初 helper 写在 conftest.py 顶层 → pytest --collect-only 抛 PluginValidationError → 5 条登录用例全部 collect 失败。迁到 common/data_loader.py 后 collect-only 立刻输出 10 tests collected。

4.3 概念 3：fixture scope 设计（session 复用 + function 兜底）

5 个 fixture 分两种 scope：

    style E fill:#fef9e7,stroke:#888

为什么 auth_token 用 function scope？

  • session 级：所有用例共享同一个 token——登录一次，跑完 10 条用例；速度最优。
  • function 级：每条用例新登录——session 内缓存复用，避免每次都打 /login 接口；平衡速度 + 隔离。
  • 本课用 function 触发 + session 缓存 混合：auth_token 是 function 级（保证每次都能取到最新），但内部读 _session_token_cache（避免重复登录）。
scope 金句
session 太宽（多用户 / 多 token 场景难处理），function 太窄（10 条用例 × 5 秒登录 = 50 秒浪费）；session 缓存 + function 触发是中间路径。

4.4 概念 4：allure 优雅降级（用户没装也能跑）

common/allure_compat.py（74 行）实现"装了 allure 用真 allure，没装 allure 用 identity / no-op"——核心代码：

try:
    import allure as _real_allure
    _HAS_ALLURE = True
except ImportError:
    _HAS_ALLURE = False

if _HAS_ALLURE:
    attachment_type = _real_allure.attachment_type
    _attachment = _real_allure.attach
else:
    attachment_type = _AttachmentType  # 占位类
    def _identity_decorator(*_args, **_kw):
        def _wrap(obj): return obj
        return _wrap
    def _noop_attach(*_args, **_kw): return None
    _attachment = _noop_attach

def feature(name: str):
    if _HAS_ALLURE:
        return _real_allure.feature(name)
    return _identity_decorator(name)

# 测试文件统一用法：from common import allure_compat as allure
# @allure.feature("登录") → 真 allure 装饰 or identity 装饰

效果：

  • 用户装了 allure-pytest：@allure.feature 是真装饰器，allure.attach 真附件，bash run.sh 后 allure serve reports 能看完整报告。
  • 用户没装：@allure.feature 是 identity 函数（直接返回被装饰对象），allure.attach 是 no-op，pytest --collect-only 照样输出 10 tests collected，pytest -v 照样跑 10 条。
降级金句
"框架不应该因为用户没装某个第三方包就跑不起来"——这是 api-auto 的设计底线：装 allure 出报告，不装 allure 也能跑测试，只丢报告装饰。

4.5 概念 5：skip 标记处理待环境用例

test_prod.py + test_order.py 共 5 条用例（3 prod + 2 order）需要 PROD_ID / SKU_ID / SHOP_ID / ADDR_ID 等真实 ID——用户启 8086 之前这些 ID 没回填。用 pytest.mark.skip + skipif 兜底：

# test_prod.py — 3 条商品用例
@pytest.mark.skipif(
    not os.getenv("PROD_ID") or os.getenv("PROD_ID") in ("", "1"),
    reason="env.PROD_ID 未填或仍为占位 '1'，待用户回填真实 prodId 后解除 skip",
)
@pytest.mark.p1
@allure.story("商品详情")
def test_prod_info(self, api_client):
    """GET /prod/prodInfo — 商品详情。"""
    ...

@pytest.mark.skip(reason="env 数据未回填，待用户启 8086 后从 tz_prod / tz_sku 查真实 ID 后解除 skip")
@pytest.mark.p1
def test_page_prod(self, api_client): ...

@pytest.mark.skip(reason="env 数据未回填，待用户回填 PROD_ID / SKU_ID 后解除 skip")
def test_get_sku_list(self, api_client): ...

# test_order.py — 2 条订单用例（同款 skip 模式）
@pytest.mark.skip(reason="env 数据未回填，待回填 PROD_ID/SKU_ID/SHOP_ID/ADDR_ID + token 后解除 skip")
def test_confirm(self, api_client): ...

@pytest.mark.skip(reason="env 数据未回填，待回填后解除 skip")
def test_submit(self, api_client): ...

3 条 skip + 1 条 skipif 效果：

  • 默认状态（.env 不存在）：PROD_ID 空 → test_prod_info skipif 触发；其他 4 条硬 skip。5 条全 skip，collect 仍收集 10 条。
  • 用户回填后：去掉 skip 标记 + 删 skipif 兜底，pytest -v 跑这 5 条。
skip vs xfail
skip = 无条件不跑（环境没准备好）；xfail = 期望失败（已知 bug 但暂不修）；skipif = 条件不跑（动态检查）。本课 5 条用例是 skip，不是 xfail——它们不是"已知 bug"，而是"环境未就绪"。

5. 动手练：5 分钟装依赖 + collect-only 看 10 条用例

学完概念后，5 分钟亲手跑一遍，这是 L10 的 win 产物——不需要后端启服务（10 条用例里 5 条登录可立刻跑，其他 5 条默认 skip）。

  1. 任务 A：装依赖——cd test-cases/api-auto → pip install -r requirements.txt（pytest 8.3 / requests 2.32 / allure-pytest 2.13 / pyyaml 等）。
  2. 任务 B：copy env——cp .env.example .env（先不填，让 5 条商品 / 订单 skip）。
  3. 任务 C：collect-only——pytest --collect-only testcases/，应看到 10 tests collected（5 login + 3 prod + 2 order）。
  4. 任务 D：单独跑 login——pytest -v testcases/test_login.py，看 5 条登录参数化的展开（test_login[case0] ~ test_login[case4]）。如果后端没启，5 条会全部失败——没关系，看到 5 个测试 ID 已展开即可。
  5. 任务 E：查看 allure 降级（可选）——故意 pip uninstall allure-pytest（或干脆不装），再跑 pytest --collect-only，依然 10 tests collected——这就是优雅降级。

  • ✅ pytest --collect-only 输出 10 tests collected
