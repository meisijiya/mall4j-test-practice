1. 为什么测试需要阶梯压测 + 调优复测（单点 ≠ 全景）

D10 单点压测 100u/60s 只能回答"100 用户能不能扛"，不能回答"系统极限在哪 / 拐点在哪 / 调优后提升多少"。

阶梯压测回答的问题：

  • 拐点：用户数从 200 涨到 500，TPS 不涨反降 → 系统极限在 200 用户
  • 瓶颈：CPU 100% / 内存 80% / DB 连接池 100% → 哪个先触顶
  • 调优空间：调优前 50u 时 P99=800ms，调优后 50u 时 P99=300ms → 提升 60%

反例：某电商调优后宣称"TPS 提升 3 倍"——但调优前是 100u/30s，调优后是 50u/60s（不同条件），面试官深问就露馅。

2. 3 场景脚本设计（login/query/order 5 endpoint）

2.1 场景 1：登录（locustfile_login.py 144 行）

  • 复用 D10 locustfile.py 的 on_start adminLogin 套路
  • 3 个 @task：view_prod_list 60% / view_prod_detail 30% / view_my_info 10%
  • NUM_USERS 环境变量支持阶梯覆盖（50/100/200/500）

2.2 场景 2：商品查询（locustfile_query.py 133 行）

  • 不登录（匿名访问）—— 模拟未登录用户浏览

  • search_by_tag 调 /prod/prodListByTagId?tagId=N 测试缓存命中

2.3 场景 3：下单链路（locustfile_order.py 202 行）

  • on_start adminLogin 拿 token
  • 3 个 @task：order_list 40% / order_detail 30% / cart_list 30%
  • 故意不调 /order/submit（涉及资金事务，避免误测导致真实扣款）
# 3 场景独立跑次 × 4 阶梯 × 2 轮 = 24 个 locust 实例
STEPS="50 100 200 500"
for USERS in $STEPS; do
    for SCENARIO in login query order; do
        locust -f "locustfile_${SCENARIO}.py" \
            --users $USERS --spawn-rate 10 --run-time 60s \
            --headless --only-summary \
            --html reports/{before,after}/L$((USERS/50))-${SCENARIO}-report.html \
            --csv reports/{before,after}/L$((USERS/50))-${SCENARIO}-stats
        sleep 30   # JVM 缓存预热 + GC 触底 + HikariCP 回收
    done
done

3. 4 阶梯调度 + 间隔 30s（JVM 预热 + GC 触底）

3.1 为什么 50/100/200/500 而不是 100/300/500/1000？

  • 50u：基线（无压力）
  • 100u：D10 单点压测（参考线）
  • 200u：2 倍 D10（找拐点）
  • 500u：极限（单实例 Spring Boot 容易 OOM）

3.2 为什么阶梯间隔 30s？

  • JVM 缓存预热：HikariCP 连接池从 min-idle=10 涨到 maximum-pool-size=30 需 ~10s
  • GC 触底：堆内存从用户瞬时峰值回落到 baseline 需 ~5s
  • HikariCP 回收：超时连接回收 + 新连接预热 ~15s
  • 合计：30s 是"既不闲等也不卡 GC"的经验值

3.3 间隔期 JVM 状态采样命令

# 间隔期做 4 项采样，确认 JVM 真触底再跑下一阶梯
PID=$(pgrep -f 'yami-shop-api.*\.jar' | head -1)
echo "--- JDK 线程数 ---"   ; jstack $PID | grep -c '^"'
echo "--- 堆内存 ---"      ; jstat -gc $PID | awk '{print "Eden="$6"K  Old="$8"K  Meta="$10"K"}'
echo "--- GC 计数 ---"     ; jstat -gcutil $PID | awk 'NR==2 {print "YGC="$2"  FGC="$4}'
echo "--- DB 连接池 ---"   ; curl -s http://127.0.0.1:8086/actuator/hikari | jq '.pools.HikariPool.active'
# 任一项异常 → sleep 再补 30s，否则启动下一阶梯

4.2 mall4j 调优铁律：AGPLv3 不动 Java 源码

  • ✅ 可用：Tomcat 线程池 / HikariCP / Lettuce / JVM 参数（全部走 .properties + -Xmx）
  • ❌ 禁用：加锁粒度细化 / 内存泄漏修复 / 业务逻辑优化（违反 AGPLv3 不变量 1）

4.3 tuning-config.properties 关键 3 段

# 1. Tomcat 线程池（默认 200 → 400）
server.tomcat.threads.max=400
server.tomcat.threads.min-spare=50

# 2. HikariCP 连接池（默认 10 → 30）
spring.datasource.hikari.maximum-pool-size=30
spring.datasource.hikari.minimum-idle=10

# 3. Lettuce Redis 池（默认 6 → 20）
spring.redis.lettuce.pool.max-active=20
spring.redis.lettuce.pool.max-idle=10

4.4 tuning-jvm.sh 应用方式

#!/usr/bin/env bash
set -euo pipefail
pkill -f "yami-shop-api.*\.jar" || echo "ℹ️ 无旧 java 进程"

java -jar yami-shop-api/target/yami-shop-api-0.0.1-SNAPSHOT.jar \
    --spring.profiles.active=dev \
    --spring.config.additional-location=file:./tuning-config.properties \
    -Xmx1g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
    > api.log 2>&1 &

echo "✅ 调优后 API 启动"
sleep 30
curl -s http://127.0.0.1:8086/doc.html > /dev/null && echo "✅ API ready"

5. 思考题 + mall4j 全阶段收尾

Q1：4 阶梯间隔 30s 是闲等还是有意义？答：JVM 缓存预热（HikariCP 连接池从 min-idle 涨到 maximum-pool-size）+ GC 触底（堆内存回落）+ 连接池回收（超时连接回收）—— 30s 是经验值，不是闲等

Q2：调优决策树第一步看 CPU 还是内存？答：CPU 100% 是第一信号（JVM 线程 dump 有 BLOCKED → 锁竞争 / 无 BLOCKED → CPU bound）；内存 80% 是第二信号（GC 频繁 → JVM GC / 不频繁 → 内存泄漏）

Q3：mall4j 调优能改 Java 源码吗？答：❌ 不能（AGPLv3 不变量 1）；调优全部走 .properties（Tomcat 线程池 / HikariCP / Lettuce）+ JVM 参数（-Xmx1g + G1GC）—— 不动 yami-shop-* Java 文件
