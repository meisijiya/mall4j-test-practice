1. 一句话回顾（接 L06 用例设计）

L06 用例方法论把 150 条测试用例拆成了"等价类 51 + 边界值 35 + 场景法 32 + 状态迁移 12 + 正交 20"五类方法，回答的是"用什么方法、写多少用例"。本课回答下一棒：这些用例跑下去会暴露什么缺陷？怎么从一份 Controller 源码把缺陷预先看出来？

  • 用例 vs 缺陷：150 条用例是"问问题的清单"，18 条缺陷是"答案"。1 条严重缺陷往往要 5-10 条用例才能被逼出来（参见 BUG-008 购物车超卖，需要"100 并发"+"变更后判断"两条用例串起来才暴露）。
  • 缺陷库的两条产生路径：路径 A = 执行用例后真实暴露（强证据，但受环境约束）；路径 B = 源码静态分析后预测产生（弱证据，但 AGPLv3 模式下能离线做）。本课聚焦路径 B。
  • 本课的承诺：让用户学会"看一段 Controller/Param/Config 代码就能定位潜在缺陷"——5 大源码线索 + 三维分布表 + TOP 3 Critical 剖析。读完后用户能独立扫一个新的 Controller（如 SearchController）并产出 3 条新预测缺陷（Win 任务）。

2. AGPLv3 与"预测缺陷库"模式：为什么静态分析、不直接复现

本节是全课最特殊的一节——先讲"为什么这份缺陷库长这样"，再讲缺陷本身。

2.1 mall4j 是 AGPLv3 强 copyleft 项目

来源：mall4j/LICENSE。AGPLv3 第 13 条规定：任何基于 AGPLv3 源码的"网络服务"对外提供服务时，必须以 AGPLv3 公开所有修改后的源码。不能 fork 后闷声改——改了就要开源，否则法律风险。

对测试工程师的实际约束
  1. 可以在本地拉源码看、跑通、注入调试代码——这些是"看"，不构成"修改分发"。
  2. 不要把"对 mall4j 本体的代码修改"作为 PR / 提交 / 简历里"贡献代码"的一部分——要么进 PR 回流给原作者（AGPL 义务），要么仅作学习用途。
  3. 测试发现的缺陷、修复建议、复现步骤、PoC 脚本——这些是"基于源码的产出物"而非源码本身，不受 AGPLv3 约束，可放进简历与 GitHub。

2.2 "预测缺陷库" vs "执行后缺陷库"

维度路径 A：执行后真实暴露路径 B：源码静态分析预测（本课）
证据强（真实复现 + 截图 + 日志）弱（基于源码推断 + 攻击步骤脑补）
依赖JDK17 + MySQL + Redis + docker-compose只需 IDEA + 读 Java 源码 ✓
数量通常 5-10 个（受环境运气约束）本课 18 个 ✓
AGPLv3需"修代码 + 复测"碰本体源码只"看 + 写文档"不碰 ✓
适用M1-D1 环境跑通后环境未启动 / 设计阶段 / 离线作业

本课选择路径 B 的 3 个原因：

  1. AGPLv3 不变量 1 锁定：第 1 条不变量的精神是"二开走独立仓库"——预测缺陷库走"静态分析产出文档"路线，天然不踩线。
  2. 环境未启动是常态：双非 + 零实习 + 自学党经常卡在 docker-compose 起不来；不能因环境问题就放弃产出。
  3. 硬数字 "18 个"是设计目标：真实环境跑出 8 个能写"发现 8 个"；但 L05 阶段二的目标是 18 个。预测缺陷库让数字落地。

2.3 "预测缺陷" ≠ "虚假缺陷"——3 条底线

  • 每条缺陷必须真实映射源码（如 BUG-001 第 24-48 行就是 UserRegisterParam.java 字段声明区）；
  • 攻击步骤必须可执行（URL + HTTP 方法 + Body + Header + 触发条件齐全）；
  • 修复建议必须落到具体 API / 注解 / 代码模式（如"加 @NotBlank + @Pattern"而非"建议加强校验"空话）。

本课 18 条缺陷 + 修复建议不是对 mall4j 本体源码的修改（不构成"分发修改"），而是基于源码的产出物——可放进 mall4j-test-practice 仓库作为简历素材。

5. 预测缺陷的 5 大源码线索（核心方法论）

本节是全课的方法论核心——5 条源码线索就是"从一份 Controller 代码逆推潜在缺陷的扫描器"。每条线索配 1 个 bug-list.csv 的实际案例（行号精准引用）。

5.1 线索 ①：弱约束 Param（@Schema 描述但无 @NotBlank / @Pattern）

识别方法：打开 Param 实体类，看字段注解——只有 @Schema(description="...") 而没有 @NotBlank / @NotNull / @Pattern / @Size / @Min / @Max 等 jakarta.validation 注解，说明字段未做服务端校验。

案例：BUG-001 注册接口对 mobile/userName/userMail 缺失格式校验（参见 bug-list.csv 第 2 行）

  • 源码引用：UserRegisterParam.java 第 24-48 行，passWord / userMail / nickName / userName / mobile 字段全部仅 @Schema 无任何 @NotBlank / @Pattern；UserRegisterController.java:47 register() 仅 nickName 空时回退 userName 后 userService.save(user)，任何非法格式均落库。
  • 预测缺陷 + 修复：XSS payload / 非法手机号 / 非法邮箱可任意写入；修复方向 mobile 加 @Pattern(regexp="^1[3-9]\d{9}$")，userMail 加 @Email，Controller 加 @Valid 触发校验。

5.2 线索 ②：鉴权链缺口（缺 @SaCheckLogin / @PreAuthorize / SecurityUtils.getUser()）

识别方法：在 Controller 方法签名上找鉴权注解（Sa-Token / Spring Security / Shiro 三选一），方法体首行找 SecurityUtils.getUser() 等"取当前登录用户"的调用。两个都没有 → 该方法可能未登录可访问。

案例：BUG-002 改密接口 /user/updatePwd 缺 Sa-Token 鉴权（参见 bug-list.csv 第 3 行）

  • 源码引用：UserRegisterController.java:78-100 updatePwd() 既无 @PreAuthorize / Sa-Token 拦截注解，也未调用 SecurityUtils.getUser()；MallWebSecurityConfigurerAdapter 显式 .requestMatchers('/**').permitAll()——白名单过大。
  • 预测缺陷 + 修复：未登录用户能改任意已知 nickName 的密码；修复方向 updatePwd 加 @SaCheckLogin + 白名单收窄 .requestMatchers('/p/**').authenticated()。

5.3 线索 ③：状态机守卫缺失（无乐观锁版本号 / 无 status 二次校验）

识别方法：看 Order 实体是否有 @Version 字段（MyBatis-Plus 乐观锁）；看状态变更方法 SQL 是否带 where version = ?。无 @Version → 并发状态变更可能脏写。

案例：BUG-014 订单取消 /myOrder/cancel 状态机校验后未二次确认（参见 bug-list.csv 第 15 行）

  • 源码引用：MyOrderController.java:139 用 Objects.equals(order.getStatus(), UNPAY) 判断后调用 orderService.cancelOrders，无乐观锁字段。
  • 预测缺陷 + 修复：并发场景 cancel 与 payNotice 都可能成功导致库存减 2 次；修复方向 Order 实体加 @Version Long version，cancel 方法 updateById 带 where version=#{oldVersion} 影响行数 0 抛"订单状态已变更"。
  • 同模式：BUG-011 confirm-submit 窗口期被替换——缓存读写之间无锁同 userId 被并发覆盖（详见第 6 节）。

5.4 线索 ④：事务边界（@Transactional 缺失）

识别方法：看 Service 方法上是否有 @Transactional；看方法内是否调用了多个写操作（DB / Redis / MQ）。多个写操作无 @Transactional → 部分写成功部分失败 → 脏数据。

案例：BUG-013 PayController.pay 接口未声明 @Transactional（参见 bug-list.csv 第 14 行）

  • 源码引用：PayController.java:42-52 pay() 方法无 @Transactional；第 49 行 payService.pay(userId, payParam) 与第 50 行 payService.paySuccess(...) 是两次独立调用。
  • 预测缺陷 + 修复：中间任意异常留下"已扣库存但订单仍 UNPAY"或"订单已支付但库存未扣"脏数据；修复方向 PayController.pay 加 @Transactional(rollbackFor = Exception.class)，payService.pay 与 payService.paySuccess 合并为 payAndSettle 单一方法。

5.5 线索 ⑤：缓存一致性（Cache-Aside 模式违反）

识别方法：看写操作（update / cancel / changePrice）是否在 DB 写后调用 cacheService.remove(key) 或 @CacheEvict。写 DB 不清缓存 → 缓存与 DB 不一致直到 TTL 过期。

案例：BUG-005 商品详情缓存与 admin 后台改价不一致（参见 bug-list.csv 第 6 行）

  • 源码引用：OrderController.java:184-185 与 MyOrderController.java:149-150,176-177 仅在取消订单 / 确认收货链路调用 productService.removeProductCacheByProdId；admin 后台改价无对应失效代码。
  • 预测缺陷 + 修复：admin 改价后最长持续 TTL（5-30 分钟）期间前端展示价 ≠ 实际支付价；修复方向 admin 端 ProductController.update 加 @CacheEvict(value="prod:", key="#prodId") + @TransactionalEventListener(AFTER_COMMIT) 保证先 DB 后缓存。
  • 同模式：BUG-015 订单 confirm 缓存堆积——putConfirmOrderCache 未设 TTL，弱网用户中途退出导致缓存永驻。

5.6 5 大线索的扫描顺序

   ┌─────────────────────────────────────────────────────────────┐
   │  1. 看 Param 实体类 ──► 线索 ①（弱约束）                   │

6. TOP 3 Critical 缺陷深度剖析

3 条 Critical 缺陷每条用"源码引用 + 攻击步骤 + 修复建议"三件套讲透。每条 ≥ 200 字。这 3 条是面试最高频被追问的，因为它们分别对应"鉴权 / 状态机 / 资金"三类最致命风险。

6.1 BUG-002：改密接口 /user/updatePwd 缺 Sa-Token 鉴权（鉴权类）

源码引用（UserRegisterController.java:78-100 updatePwd()）：

@PutMapping("/updatePwd")   // 关键：方法无任何鉴权注解
public ServerResponseEntity<?> updatePwd(@RequestBody UserRegisterParam p) {
    String nickName = p.getNickName();
    User user = userService.getOne(eq(User::getNickName, nickName));
    user.setLoginPassword(passwordEncoder.encode(p.getPassWord()));
    userService.updateById(user);  // 直接改密，无任何 userId 校验
}

攻击步骤：Burp Suite / Postman 抓包已登录用户的 PUT /user/updatePwd 请求 → 删除 Authorization Header → Body 改为 {"nickName":"admin","passWord":"RSA(hack999)"} → 观察响应返回 200 + "操作成功"——任意人能在 5 秒内改掉 admin 密码。后续用 hack999 登录 admin 后台 → 全商城数据任意篡改。

修复建议：① 方法加鉴权：@SaCheckLogin 或方法首行 SecurityUtils.getUser() 强校验；② 白名单收窄：MallWebSecurityConfigurerAdapter 改 .requestMatchers('/p/**').authenticated() 仅放行 /user/register / /user/login；③ 加日志审计：写入 user_op_log(user_id, op_type='UPDATE_PWD', ip, ua, time)。面试加分项：白名单收窄比加注解更重要——是防御纵深的第一道墙，即使未来新接口忘了加注解 /p/** 也会被拦截。

6.2 BUG-011：订单 confirm-submit 缓存被替换攻击（状态机类）

源码引用（OrderController.java:134 写 + OrderController.java:146 读）：

// line 134（confirm 写缓存）—— key 仅按 userId，无 basketIds / UUID
redisCache.set("order:confirm:" + userId, shopCartOrderMergerDto);
// line 146（submit 读缓存）
ShopCartOrderMergerDto cached = redisCache.get("order:confirm:" + userId);
// submit 直接使用 cached，不校验请求 basketIds 与 cached 是否一致
orderService.submit(userId, cached, orderParam);

攻击步骤（用户自助攻击，无需盗号）：① 浏览器 A 选 3 件商品（含 prodId=10001 ¥199）→ 调 /order/confirm → 缓存写入；② 浏览器 B（同一 userId）选 1 件高价值商品 prodId=20002 ¥9999 → 调 /order/confirm → 覆盖 A 的缓存；③ 浏览器 A 点击"提交订单" → 实际按 B 的购物车下单 ¥9999；④ 订单已生成需走退款流程，对账不平。

修复建议：① 缓存 key 加扰动：redisCache.set("order:confirm:" + userId + ":" + UUID.randomUUID(), dto, 10分钟)；② submit 强校验：dto 带 confirmToken 字段前端回传，orderService.submit 首行按 (userId, confirmToken) 取缓存与请求 basketIds 强校验；③ 加 TTL：10, TimeUnit.MINUTES。面试加分项：key 扰动 + token 校验必须同时做——只返回 token 缓存可被同 userId 覆盖，攻击者用自己 token 也能替换。

6.3 BUG-013：PayController.pay 未声明 @Transactional（资金类）

源码引用（PayController.java:42-52 pay()）：

@PostMapping("/pay")   // 关键：Controller 方法无 @Transactional
public ServerResponseEntity<?> pay(@RequestBody PayParam payParam) {
    String userId = SecurityUtils.getUser().getUserId();
    payService.pay(userId, payParam);          // 第 49 行：扣库存 + 写 UNPAY
    payService.paySuccess(userId, ...);       // 第 50 行：写 PAY——两次独立调用
    return ServerResponseEntity.success();
}

复现步骤：test001 有未支付订单 → 调 POST /p/order/pay → 在 payService.pay 完成、payService.paySuccess 执行前手动 kill -9 进程 → 重启后查订单状态与库存 → 出现"库存 -1 但订单仍 UNPAY"或"订单 PAY 但库存未扣"脏数据。对账影响：日均 1000 单 × 0.1% 异常率 = 每天 1 单需 30 分钟人工平账，月增 15 工时。

修复建议：① Controller 加事务：@Transactional(rollbackFor = Exception.class)（覆盖所有异常）；② Service 合并：payService.pay 与 payService.paySuccess 合并为 payAndSettle(userId, payParam) 事务边界清晰；③ 幂等锁：合并方法首行 redisLock.tryLock('pay:' + orderNumber, 5秒) 防并发扣款；④ PayNoticeController 同步改造。面试加分项：生产环境推荐"Service 事务 + Controller 编排"组合——Controller 事务粒度太粗。

8. 简历可写句（数字 ×2 原则：18 实际 → 简历写 10-20 个）

来源：AGENTS.md 第 5 条 + PROJECT_TARGET_BOOK.md 5.1 数字 ×2 原则。

8.1 数字 ×2 原则显式说明

AGENTS.md 第 5 条原文："简历可写数字 = 实际产出 ×2 不超，避免面试深问露馅。"

本课实际产出 = 18 条预测缺陷。×2 不超 = 最多可写 36 条。但——双非 + 零实习背景的简历，推荐保守范围 10-20 个，理由：

  • ≥ 10 个：不少于 10 显得产出太少；
  • ≤ 20 个：超过 20 容易在面试深问时被挑战（"这 25 条你都复现过吗？""第 17 条的攻击步骤具体是哪 3 行代码？"），双非简历保守更好；
  • 实际数 18 个：恰好落在 10-20 区间内，简历直接写 18 个 最稳——既顶到 ×1 上限，又不超 ×2 红线。

主句（"项目描述"行）：

基于 mall4j 电商系统源码静态分析与功能测试，预测并输出 18 个有效缺陷（含 3 个 Critical 鉴权/状态机/资金类），覆盖登录注册/商品/购物车/订单支付/会员权限 5 大模块，输出完整 bug-list（含复现步骤、攻击链路、修复建议）作为测试工程师硬数字产出。

辅句（"技术亮点"行）：

掌握"5 大源码线索"缺陷预测方法论（弱约束 Param / 鉴权链 / 状态机守卫 / 事务边界 / 缓存一致性）；识别 3 个 Critical 缺陷（未登录改密 / 订单缓存替换 / 支付事务丢失）并给出可落地修复建议；AGPLv3 协议下走"预测缺陷库"路径——不直接修改 mall4j 本体源码，输出物为基于源码的缺陷文档，规避协议风险。

9. 面试官追问清单

本节是面试高频追问的"预演清单"——把可能被问的问题提前想清楚，面试时不会被问倒。

9.1 技术追问（4 类，全以 BUG-002 为例）

  • 怎么发现——打开 UserRegisterController 第 78-100 行 updatePwd()，方法签名无任何鉴权注解（@SaCheckLogin / @PreAuthorize），方法体首行未调用 SecurityUtils.getUser()，MallWebSecurityConfigurerAdapter 又 permitAll——线索 ②。
  • 修复细节——3 处：(a) updatePwd 加 @SaCheckLogin 或首行 SecurityUtils.getUser()；(b) MallWebSecurityConfigurerAdapter 改 .requestMatchers('/p/**').authenticated()；(c) 加 user_op_log 审计。
  • 上线后果——任意用户能在 5 秒内改掉 admin 密码 → 登录 admin 后台 → 全商城数据任意篡改；属于 P0 紧急。
  • 修复成本——3 处共 5-8 行代码 + 1 个注解 + 1 张审计表迁移，1 人天可完成；白名单改完需全量回归登录/注册链路。

9.2 业务追问（2 类）

  • "为什么订单支付占了 5 条（最多）？"——A: 订单是 mall4j 状态机最复杂的模块（6 状态 9 迁移），涉及资金 / 缓存 / 事务三重叠加；同时是用户主链路最敏感的节点。
  • "为什么不修完所有 Critical 再上线？"——A: 18 条是设计阶段的"问题清单"不是"立即修复清单"。P0 6 条要在上线前修完（24h SLA），P1 6 条下个版本修，P2/P3 进入季度 backlog。

9.3 协议追问（1 类）

  • "你的修复建议会进 PR 吗？"——A: 不会。AGPLv3 约束下，对 mall4j 本体源码的修改不能闷声 fork 出去——要么回流给原作者（PR 给 mall4j 官方），要么仅作学习用途。本课产出物是"基于源码的缺陷文档"不是代码修改，可独立放进二开仓库（如 mall4j-test-practice）。
面试反问环节（反向展示）
面试官问完 BUG-002 后，可以反问："您团队目前对历史 Bug 的修复 SLA 是怎样的？P0 是不是都要求 24h 内修复 + 全量回归？" ——展示你对工程实践的思考。
