## 2. 七大模块边界（后端源码包 + 测试归属）

来源：`CONTEXT.md` 第 17-28 行 + `doc/1-项目概览/3-后端模块说明.md`。

mall4j 后端是 Maven 多模块工程，**业务归属 ≠ 包路径**：同名业务会在两个后端模块（用户端 + 管理端）各有一个 Controller。测试用例**必须按业务模块**而非物理包来划分。

| 模块 | 源码包（用户端） | 源码包（管理端） | 测试归属（写在哪） | 主测试方法 |
|---|---|---|---|---|
| **商品与 SKU** | `yami-shop-api/.../prod` | `yami-shop-admin/.../prod` + `yami-shop-service/.../ProdService` | 商品查询 / SKU 选择 / 库存扣减 | 等价类（库存=0/正常/超量）+ 边界值 |
| **订单与支付** | `yami-shop-api/.../order` + `.../pay` | `yami-shop-admin/.../order` | 状态机迁移 / 回调幂等 / 退款链路 | 状态迁移（每个状态 3 条用例）+ 场景法 |
| **购物车** | `yami-shop-api/.../cart` | （无） | 加车 / 改数 / 删除 / 优惠叠加 | 等价类 + 边界值 |
| **会员** | `yami-shop-api/.../member` | `yami-shop-admin/.../user` | 注册 / 登录 / 地址簿 / 余额 | 场景法 + 异常分支 |
| **权限** | （鉴权拦截所有 API） | `yami-shop-security-admin` + `yami-shop-admin/.../sys` | Sa-Token 鉴权 / 角色-菜单-数据权限 | 边界值（4 道关卡，见第 3 节） |
| **统计** | （无） | `yami-shop-admin/.../stat` | 运营报表聚合查询 | 等价类 + 时间窗 |
| **优惠券 / 营销** | `yami-shop-api/.../coupon` | `yami-shop-admin/.../coupon` | 领取 / 使用 / 叠加规则 | 场景法（互斥 / 叠加） |

**关键判断**：**接口契约唯一可信源 = `yami-shop-api` 的 Knife4j**，路径 `/doc.html`（默认 `localhost:8086/doc.html`）。管理端的 API 文档通常比用户端滞后，写接口自动化时**优先以用户端为准**做参考。

**测试归属 = 写在哪**：指 pytest 用例的目录结构。一个业务模块的用例**至少 4 个文件**（test_api_user.py / test_api_admin.py / test_ui.py / test_perf.py），而不是一个文件里堆所有用例。

**反模式**：按"Controller 数量"来切分测试文件——会出现一个文件 800 行，谁也看不懂。**正确做法**：按业务模块切分，跨模块的横切关注点（鉴权/幂等/分布式锁/参数校验/分页）走独立测试集。

## 3. 鉴权链（Sa-Token）四必测

来源：`doc/4-技术实现/1-权限体系.md` + `CONTEXT.md` 第 31-35 行。

mall4j 用 **Sa-Token** 做鉴权，`yami-shop-security-admin` 是鉴权入口。鉴权链是**所有接口**的前置关卡，每个接口测试都必须先过这四道关：

### 3.1 鉴权四必测

| 编号 | 场景 | 期望 | 触发代码入口 |
|---|---|---|---|
| **A1** | 不带 token 调任意需要登录的接口 | 401 / `UNAUTHORIZED` | Sa-Token 拦截器 → `AuthUtil.getToken()` 为空 |
| **A2** | 带过期 token 调接口 | 401 / `TOKEN_EXPIRED` | Sa-Token 拦截器 → `Token timeout` 异常 |
| **A3** | 普通用户（普通会员角色）访问 admin 接口 | 403 / `FORBIDDEN` | `@PreAuthorize("@pms.hasPermission(...)")` 不匹配 |
| **A4** | 多角色用户登录（如同时拥有"运营 + 客服"） | 按 `tz_sys_menu` 的 `role_id` 取并集返回菜单 | `GET /sys/menu/nav` 返回 `menuList` |

### 3.2 测试归属

- **接口自动化**：在 conftest.py 里造 4 个 fixture（`no_token` / `expired_token` / `user_token` / `admin_token`），每个接口测试至少覆盖 A1+A3 两条。
- **UI 自动化**：用 Playwright 打开 mall4v 登录页，故意输入错误密码 → 期望跳回登录页 + 提示"账号或密码错误"。
- **性能**：1000 并发带过期 token 调接口 → 期望**不被穿透**到 Service 层（验证拦截器在 Filter 链的最前面）。

**反模式警告**：只测 A1（不带 token）就声称"鉴权测过了"——A2/A3/A4 才是线上最常爆雷的点。A3（垂直越权）是 OWASP Top 10 之一，A4（菜单越权）会让运营看到不该看的菜单。

## 4. 幂等性三必测（订单 / 支付 / 退款）

来源：`CONTEXT.md` 第 37-40 行 + 第 2 课支付幂等三道关。

幂等性 = **同一个请求执行 N 次，结果只发生一次**。mall4j 资金流相关的接口**每一个都必须测幂等**，否则线上会出"一单扣两次款"的生产事故。

| 编号 | 场景 | 期望 | 代码入口 |
|---|---|---|---|
| **I1** | 同一订单号（orderNumber）重复点"提交订单" | 仅成功一次，第二次返回"订单已存在"或快照已过期 | `OrderController.submitOrders` → `ConfirmOrderCache` userId 维度 + `tz_order` 唯一索引 |
| **I2** | 同一支付回调（payNo）多次到达 | 仅更新一次订单状态，后续回调幂等返回 | `PayNoticeController`（开源版注释）+ `OrderSettlementMapper.updateToPay()` 乐观锁 `version+1` |
| **I3** | 同一退款请求（refundNo）多次提交 | 仅退一次，`tz_order_refund.return_money_sts` 不重复置 1 | `RefundController.applyRefund` → `tz_order_refund` 唯一索引 + 状态机校验 |

### 测试设计要点

- **I1 测试方法**：在用户端调一次 `submitOrders`，拿到 orderNumber 后**不刷新页面直接重发同一请求** → 期望第二次返回业务错误码（`ServerResponseEntity.fail(...)`）。
- **I2 测试方法**：用 curl 重放支付回调（带相同 payNo + sign）至少 3 次 → 期望业务表只更新 1 次，资金流日志只写 1 条。
- **I3 测试方法**：用户发起退款，商家在管理端重复点"同意退款" → 期望第三方退款接口只被调 1 次。

**反模式**：只测"正常下单一次能成功"——这是单点通过，幂等路径完全没覆盖。

## 5. 分布式锁（Redisson）：秒杀 / 库存并发不超卖

来源：`doc/4-技术实现/7-分布式锁.md` + `CONTEXT.md` 第 42-44 行。

mall4j 提供 `@RedisLock` 注解（基于 Redisson），但**当前业务代码里暂未发现实际使用点**（二开常见位置：库存扣减、重复提交、并发状态流转）。即使开源版没启用，**写测试用例时仍要预留场景**——一旦二开启用，立刻有测试覆盖。

### 5.1 锁机制三要素

```text
Redis key 规则: redisson_lock:{lockName}:{SpEL解析结果}
默认过期: 5000 ms（防止死锁）
注解: @RedisLock(lockName = "stock", key = "#prodId")
```

### 5.2 必测点（性能测试范畴）

| 编号 | 场景 | 期望 | 失败模式 |
|---|---|---|---|
| **L1** | 同一商品 100 并发扣减库存（库存预置 50） | 最终库存 = -50 之前的 0，成功订单 = 50，**不超卖** | 没加锁 → 100 个请求都看到 stock=50 → 超卖 50 个 |
| **L2** | 同一订单号 50 并发提交 | 仅成功 1 次，其余返回"重复提交" | 没加锁 → 同一订单被扣 2 次款 |
| **L3** | 锁过期时间边界：业务执行 4.9s（接近 5000ms 默认值） | 锁未失效，第二个请求被阻塞 | 锁过早释放 → 第二个请求抢到锁 → 并发问题 |

### 5.3 测试归属

- **接口 + 性能组合**：用 Locust 跑 L1，200 并发用户抢购 50 件商品，期望 success=50 / fail=150。
- **接口自动化**：在 conftest.py 里造"加锁前 / 加锁后"两个接口，分别调 → 加锁后的接口应当 `ServerResponseEntity` 提示"系统繁忙"。

**面试金句**：*Redis 分布式锁不是银弹，超时时间 + 业务执行时长必须配对；mall4j 默认 5 秒，业务超 5 秒必须显式指定 `expire`。*

## 6. 参数校验四必测（Jakarta Validation）

来源：`doc/4-技术实现/3-参数校验.md` + `CONTEXT.md` 第 46-48 行。

mall4j 用 Jakarta Validation（`@Valid` + `@NotNull` / `@NotBlank`）做参数校验，校验失败统一进 `ServerResponseEntity.fail(...)`。**每个接口都至少 4 条参数校验用例**——这是接口自动化的基本盘。

| 编号 | 场景 | 期望 | 示例 |
|---|---|---|---|
| **V1** | 必填字段缺失 | 4xx + 业务错误码 `PARAM_MISSING` | 提交订单时不传 `userAddrId` |
| **V2** | 字段类型错误 | 4xx + `PARAM_TYPE_ERROR` | `price` 字段传字符串 `"abc"` |
| **V3** | 字段长度超限 | 4xx + `PARAM_LENGTH_OVER` | 商品名称传 1000 字符（限 200） |
| **V4** | 枚举值非法 | 4xx + `PARAM_INVALID` | 订单状态传 `status=99`（仅 1-6 合法） |

### 测试设计要点

- **每个字段一条用例**：不要写"参数错误"一条用例覆盖所有字段——**字段粒度**才是接口测试的有效覆盖率。
- **边界值优先**：必填字段 → 缺失/空串/`null`/空格 各算一条；长度字段 → min-1 / min / max / max+1。
- **错误信息校验**：返回的 `msg` 字段必须包含"哪个字段错了"，不能只返回"参数错误"——否则前端没法定位。

**反模式**：在前端做校验就以为后端不用管——**前端校验可绕过**（curl / Postman / 自动化脚本），后端 `@Valid` 才是最后一道防线。

## 7. 分页边界六必测（MyBatis-Plus `PageParam`）

来源：`doc/4-技术实现/4-分页实现.md` + `CONTEXT.md` 第 50-52 行。

mall4j 分页基于 MyBatis-Plus `PageParam<T>`，默认 `current=1 / size=10`，`size` 最大限制 = 100。**所有分页接口都至少 6 条边界用例**：

| 编号 | 入参 | 期望 | 验证点 |
|---|---|---|---|
| **P1** | `current=0` | 兜底为 1 或返回 400 | MyBatis-Plus 是否 `current < 1` 自动修正 |
| **P2** | `current=-1` | 返回 400（非法参数） | Jakarta Validation `@Min(1)` 是否生效 |
| **P3** | `size=0` | 兜底为 10 或返回 400 | 默认值兜底逻辑 |
| **P4** | `size=99999` | 兜底为 100 或返回 400 | `size > 100` 截断逻辑 |
| **P5** | 总记录数 = 0 | 返回空列表 + `total=0` | 空数据路径 |
| **P6** | 总记录数 = 1 | `total=1` + `records.length=1` + 分页器显示 1 页 | 单数据路径 |

### 复杂关联分页陷阱

订单明细分页（`OrderServiceImpl.pageOrdersDetailByOrderParam()`）是**手写 SQL** + 单独 count SQL，因为 join 后行数 ≠ 订单数。测试时必须验证：

- `total` 是否等于**订单数**而非**订单项数**。
- `records` 的 `size` 是否等于当页订单项数（可能 > `PageParam.size`，因为一个订单多行）。

**反模式**：只测 `current=1&size=10`（默认参数）就声称"分页测过了"——线上 P1-P4 一旦有 Bug 就是 P0 事故。

## 8. 反模式警告：不要孤立测"商品列表能不能加载"

来源：`CONTEXT.md` 第 15 行（CONTEXT.md 第 1 节"三流合一"的最后一句）。

`mall4j` 业务要测"流"，不要测"点"——任何孤立用例都是反模式。

### 典型反模式清单

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| "商品列表能加载" | 单点通过，订单全流程可能挂 | 加载 → 加购 → 下单 → 支付 全链路 |
| "登录接口返回 200" | 只验状态码，没验 token 有效性 | 登录 → 拿 token → 调 `/sys/menu/nav` 验 token 真能用 |
| "支付回调能调通" | 没验幂等，没验金额来源 | 回调 → 验签 → 幂等 → DB 更新 → 二次回调幂等返回 |
| "退款能成功" | 没验原路返回（微信单退到支付宝） | 退款 → 查 `tz_order.pay_type` → 验退款渠道匹配 |

**判断标准**：这条用例单独跑通 ≠ 业务能跑通。**必须把"点"串成"流"**才能进用例库。

### 反例：商品列表孤立测

```python
def test_product_list_loads():
    r = requests.get(f"{BASE}/prod/page?current=1&size=10")
    assert r.status_code == 200   # ✓ 但业务完全没验证
```

**正例：商品 → 加购 → 下单 全链路**

```python
def test_browse_to_submit_order():
    # 商品列表
    products = api.list_prod_page(current=1, size=10)
    # 加购
    api.add_to_cart(prod_id=products[0]["prodId"], sku_id=products[0]["skuList"][0]["skuId"], count=1)
    # 确认订单
    confirm = api.confirm_order(cart_items=...)
    # 提交订单
    order = api.submit_orders(addr_id=..., order_items=confirm["orderItems"])
    assert order["status"] == 1  # UNPAY
    assert order["payAmount"] == products[0]["price"] * 1
```

## 9. 测试切入矩阵（模块 × 测试类型）

这是本课的"具体可验证的 win"——把这张表打印贴墙上，每个模块新增功能时按这个矩阵逐项打钩：

| 模块 \ 测试类型 | 功能 | 接口 | UI | 性能 | 异常 |
|---|---|---|---|---|---|
| **商品与 SKU** | 商品 CRUD + 上下架 | `/prod/page` / `/prod/info/{id}` | 列表页 + 详情页 | 1000 并发浏览 | 库存=0 / SKU 失效 / 商品下架 |
| **订单与支付** | 下单/支付/退款/取消 | `/order/submit` / `/pay/normalPay` / `/refund/apply` | 用户中心 + 商家后台 | 200 并发下单（幂等） | 重复下单 / 回调重放 / 支付超时 |
| **购物车** | 加车/改数/删除 | `/cart/add` / `/cart/update` / `/cart/delete` | 购物车页 | 100 并发改数 | 库存不足 / 商品失效 |
| **会员** | 注册/登录/地址 | `/register` / `/login` / `/addr/list` | 个人中心 | 500 并发登录 | 重复注册 / 错误密码 / token 过期 |
| **权限** | 角色/菜单/数据 | `/sys/menu/nav` / `/sys/role/page` | 管理后台登录 | 1000 并发带过期 token | 越权 / 菜单缺失 / 按钮不可见 |
| **统计** | 报表聚合 | `/stat/order` / `/stat/prod` | 运营报表页 | 大数据量聚合 | 时间窗越界 / 空数据 |
| **优惠券** | 领取/使用/叠加 | `/coupon/receive` / `/coupon/use` | 领券中心 | 100 并发抢券 | 券已领完 / 互斥规则 |

**矩阵用法**：

1. 每个模块新功能上线前，至少把功能 + 接口 + 异常 三列打钩。
2. UI 自动化优先覆盖"用户高频路径"（商品 → 下单 → 支付），不要为管理后台每个页面都写 UI 用例（ROI 太低）。
3. 性能测试只跑**资金流相关**接口（下单 / 支付 / 退款），其余模块用接口冒烟即可。
