1. 一句话回顾（接 L07 缺陷库 + L06 用例库）

前 5 课搭了业务/用例/流程的认知，L06/L07 把 150 条用例 + 18 个缺陷两端都落地了。本课要把这堆离散产出聚成一份能向 PM/开发汇报的文档——这就是功能测试报告。

  • 第 6 课（150 条用例库）：登录/注册 40 + 商品 30 + 购物车 20 + 订单/支付 25 + 会员/权限 15 + 兼容性/异常 20，按 7 模块切分。
  • 第 7 课（18 缺陷库）：Critical 3（鉴权缺拦截 / 状态机窗口 / 支付事务）+ Major 6 + Minor 6 + Trivial 3，按 Controller 静态分析产出。
  • 本课（9 章骨架）：把 150 用例 + 18 缺陷 + 9 章骨架三件套串成一份 Markdown 报告——即 test-cases/M1-D3-001/functional-test-report.md（17 KB / 384 行 / 9 章 28 子节）。

本课的核心论点：测试报告不是"测试结束后写一份文档"，而是从 D2 用例设计阶段就并行维护的"状态看板"。骨架的 9 章结构对应测试金字塔的 3 层（用例统计 / 缺陷统计 / 结论分析）——底座是设计（1-3 章），中层是数据（4-5 章），顶层是判断（6-8 章），地基是索引（9 章）。

2. 为什么先有骨架后填数据

两种写法决定一份报告的命运：

写法过程结果
边执行边写（推荐） D2 设计阶段就拉出 9 章骨架占位符（如 4.2 表的"已执行"列先空），每跑完一批用例就回填 actual 骨架版在 D2 末已成稿（17 KB / 384 行），数据回填只发生在 §4.5/§5.2 几处；执行完即出 v1.0
一次性写（反例） 用例跑完、缺陷归档完、复盘会开完才动笔 经常卡在 §6"结果分析"——写报告的人不记得 4 周前每条用例为什么通过/失败；交一份"数字漂亮但判断空"的报告
核心洞察（来自执行复盘）
测试报告的真正价值不是"通过率 95%"这个数字，而是判断：哪条主链路断在哪一步、为什么断、风险敞口有多大、发布要不要等。判断只能在执行当下形成，事后追写就丢了。骨架先行的本质是把"判断的容器"提前建好——每跑一条用例都顺手把容器填一行。

M1-D3-001 报告骨架就是这种写法的产物：

  • v0.1 骨架版（D3 第 2 天）：9 章全部成稿 + 28 个子节 + 11 张表头 + 占位符"(待回填)"——给 Worker A / Worker B 提供回填槽位。
  • v1.0 数据版（D1 环境跑通后，由 director 集成）：把 Worker A 跑出的 actual 与 Worker B 提交的 18 条 BUG 编号，原地替换占位符即得。

从 v0.1 → v1.0 是原地替换，不是重写——这就是骨架先行的工程价值。

6.4 §6.4 性能 + §6.5 兼容性 + §6.6 关键发现

§6.4 性能瓶颈仅作初步观察，不下结论（性能压测是 M3 阶段 JMeter / Locust 的事）。关注 4 个方法：ProdController#pageProd（N+1）/ SkuController#getSkuList（缓存命中率）/ ShopCartController#info（大列表加载）/ OrderController#confirmOrder（事务耗时）。

§6.5 兼容性观察使用 CONTEXT.md §3 可测点速查 的浏览器维度（Chrome 120 / Edge 120 / Safari 17 / Firefox 121）+ 移动端维度（mall4uni / mall4m / mall4v）+ 编码维度（UTF-8 中文 / Emoji / 超长 256 字符商品名）。

§6.6 关键发现是 PM/开发必读子节——前面 5 张表给数字，§6.6 给判断。v0.1 时本节是空的，v1.0 时由 director 在集成数据后写。典型内容：

  • 主链路整体判断：6 步全绿 → 业务通过；6 步里 X 步红 → 阻塞发布；6 步里 X ≤ 1 步黄（Major）→ 有条件发布
  • 鉴权链判断：4 类里若有 Critical 失败（如 BUG-002 改密未鉴权复现成功）→ 阻塞发布
  • 幂等性判断：3 类里任一失败 → 阻塞发布（资金安全底线）
  • 性能 / 兼容性观察：列出"观察项"，不下"上线 OK"的结论（声明交给 M3 / 兼容矩阵任务）

7.2 §8 测试结论——发不发 / 怎么发

子节回答的问题判定规则（v0.1 已写死，v1.0 只填结论）
8.1 是否达到发布标准 发不发？ ① 通过率 ≥ 95% 且 Critical 全部修复 → 建议发布
② 通过率 85%-95% 或存在 Major 未修复 → 有条件发布（附修复计划）
③ 通过率 < 85% 或存在 Critical 未修复 → 不建议发布
8.2 下一步建议 怎么发？发完干什么？ ① 修复优先级（按 5.5 TOP 5 先修 Critical/Major）② 回归范围（对应模块 P0 + 相关 P1）③ 自动化覆盖（150 条中可自动化部分 → pytest + Playwright）④ CI（GitHub Actions + Allure）⑤ 监控告警（Prometheus + 业务异常）
数字纪律（来自 PROJECT_TARGET_BOOK §5.1）
§8.1 的判定规则里"通过率 ≥ 95%"是口径，不是"凑数字"。报告里禁止写"通过率 100%"——如果 §4.5 实际回填得到 100%，一定是数据造假（150 条用例不可能全过）。诚实报告的通过率通常落在 70%-90% 之间，剩下的留给修复 + 回归 + M3 复测。

8.2 §9.3 测试数据准备清单（7 步）

附录里最实操的子节——把"环境从零到能跑"写成 7 步清单：

  1. 初始化数据库：mysql -u root -p < db/yami_shop.sql
  2. 启动后端：cd yami-shop-api && mvn spring-boot:run
  3. 启动前端：cd front-end/mall4v && pnpm dev
  4. 创建测试账号：admin 后台 → 用户管理 → 新增（5 个状态矩阵）
  5. 上架测试商品：admin 后台 → 商品管理 → 新增（≥10 个）
  6. 配置优惠券：admin 后台 → 营销管理 → 优惠券
  7. 准备 Mock 支付：启动 Mock 服务（端口见 application.yml）

要点：这 7 步的顺序不可调换——先有库才有服务，先有服务才有账号，先有账号才能跑用例。附录里写"先启动 Mock 再初始化数据库"的报告是错的。

9. 报告评审 8 条 Checklist

报告写完不是终点——PM/测试主管/开发的评审会才是终点。本节给出 8 条 Checklist，按 4 维度分组，任何一条不通过 = 报告返工。

9.1 覆盖度维度（3 条）——是否该测的都测了

#Checklist不通过的后果
1 §1.3 In-scope 与 §4.2 模块分布一一对应——In-scope 列出的 6 模块，§4.2 必须都有数据行 PM 拿 In-scope 反问 → 报告失信
2 §2.1 方法列表与 §4.3 类型分布一一对应——每种方法在 §4.3 必须有对应的用例数 "方法论只列不用" → 显得空谈
3 §6.1 主链路 6 步每步都有用例——三流合一视角下，6 步任意一步无用例 = 主链路未完整覆盖 核心业务路径断裂 → 阻塞发布

9.2 数据真实性维度（2 条）——数字能不能信

#Checklist不通过的后果
4 §4.5 + §5.6 数字自洽：通过率 + 失败率 + 阻塞率 + 跳过率 = 100%；已修复 + 修复中 + 未修复 = 总缺陷数 18 数字打架 → 报告整体失信，PM 直接打回
5 无 100% / 无完美数字——禁止出现"通过率 100%"或"修复率 100%"（150 条用例不可能全过，18 个缺陷不可能全修） 数据造假 → 测试工程师职业生涯红牌

9.3 风险闭环维度（2 条）——风险有没有结论

#Checklist不通过的后果
6 §7.3 阻塞发布问题必须为空，或每条都有"是否在 §8.1 决策中被处理"的明确归属 风险悬空 → PM 决策时无依据，回归测试不知从何开始
7 §7.1 未覆盖范围每条都有"为什么不测"的来源（CONTEXT.md §4 / M3 / i18n 留待） "为什么不测 X"反问无解 → 测试范围被反复质疑

9.4 结论可执行维度（1 条）——结论能不能照做

#Checklist不通过的后果
8 §8.1 结论二选一 + §8.2 下一步建议每条都可立即执行——三选一明确；§8.2 5 条建议每条对应明确动作 结论含糊 → PM 决策延迟 → 项目延期
Checklist 的使用方法
把这 8 条写成 report-review-checklist.md 单独存档，每次报告评审会逐条打勾。8 条全过 = 报告可发布；任意一条不通过 = 报告作者当周返工。这与第 4 课"用例评审 10 条 Checklist"是同一类治理工具——把"什么是好"的判断外化为可打分的列表。
