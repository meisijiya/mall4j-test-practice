1. 为什么测试需要 CI（本地能跑 ≠ 团队能跑）

本地 pytest -m "not ui" 6 PASS / 4 SKIP / 47 collected ≠ 同事在另一台机器也能跑通 ≠ PR 合并前自动验证。CI（持续集成）把"我能跑"变成"任何 PR 都自动跑"——这是测试开发岗从"个人跑通"升级到"团队基础设施"的硬分水岭。

CI 给测试工程师的 4 个核心价值（讲给非技术面试官听）：

  • PR 门禁：合并前必须绿（required_status_checks），防止引入回归 — — 不在线跑一遍永远不会发现"昨天接口加了鉴权 header，今天下游全 401"。
  • 定时巡检：on: schedule: cron: '0 2 * * *' 每天凌晨跑一次，发现"今天突然挂了"（依赖挂、数据库 schema 漂移）。
  • 可重现环境：runner 是干净的 ubuntu-latest（每次跑都是新 VM），本机 Windows / macOS / 依赖版本差异消失 — — 这是 CI 最值钱的特性。
  • 历史报告：allure history 30 天趋势可看（哪条用例昨天 PASS 今天 FAIL / 失败频率 / flaky 趋势）。

2. GitHub Actions 最小可投骨架

GitHub Actions workflow 文件 = .github/workflows/<name>.yml（路径固定，不能放别处），YAML 语法。下面给最小可投骨架 + 两个必备 block。

2.1 workflow 三件套（name / on / jobs）

name: API Test Pipeline
on:
  push:
    branches: [main]      # push 到 main 才触发
  pull_request:           # PR 打开也触发
    branches: [main]
  workflow_dispatch:       # 手动按钮触发（调试用）

jobs:
  test:
    runs-on: ubuntu-latest  # runner 系统
    steps:
      - uses: actions/checkout@v4          # 1. 拉代码
      - uses: actions/setup-java@v4        # 2. 装 JDK 17
        with:
          distribution: temurin
          java-version: '17'
          cache: maven                     # cache 依赖避免每次下载
      - uses: actions/setup-python@v5      # 3. 装 Python 3.11
        with:
          python-version: '3.11'
          cache: pip
          cache-dependency-path: test-cases/api-auto/requirements.txt
      - run: echo "hello ci"               # 4. 测试命令

三件套：name（workflow 显示名）+ on（什么时候触发）+ jobs.<id>（要跑什么任务）。每个 job 必须在 runs-on 上声明 runner 系统（ubuntu-latest / windows-latest / macos-latest）。

2.2 services block 启 MySQL / Redis（核心）

services:
  mysql:
    image: mysql:8.0.33                       # 镜像版本
    env:
      MYSQL_ROOT_PASSWORD: ${{ secrets.DB_PWD }}   # 密码用 secret 注入
      MYSQL_DATABASE: yami_shop
    ports:
      - 3306:3306                             # 端口映射
    options: >
      --health-cmd="mysqladmin ping"
      --health-interval=10s
      --health-timeout=5s
      --health-retries=10
  redis:
    image: redis:7.2-alpine
    ports:
      - 6379:6379
    options: >
      --health-cmd="redis-cli ping"
      --health-interval=10s
      --health-retries=10

关键点：options 里 --health-cmd + --health-interval 是确认"服务真 ready"的机制（不是启了就用，否则连不上）。runner 会等 health-cmd 成功才进下一步。L14 §4.6 网络坑会再讲。

2.3 secrets vs env 区别（面试常考）

  • secrets.*：加密存储，Settings → Secrets and variables → Actions 配置，运行时才解密（日志里自动遮蔽为 ***），适合密码 / token / API key。
  • env.*：明文写在 workflow（任何人能看），适合非敏感配置（数据库名 / 日志级别 / 端口）。
  • yml 顶部 env: 是全局变量，job 内 env: 是 job 局部变量，step 内 env: 是 step 局部变量。

3. mall4j CI 完整 workflow 解读

M2-D9-001 落地的 .github/workflows/api-test.yml 共 188 行，拆 9 个 step 全链路：

  1. checkout（actions/checkout@v4） — 拉代码（默认 shallow clone，fetch-depth: 0 才看完整历史）。
  2. setup-java17（actions/setup-java@v4） — temurin JDK17 + cache: maven，避免每次重下依赖（首次跑 3 min，缓存命中后 30 s）。
  3. setup-python3.11（actions/setup-python@v5） — Python 3.11 + cache: pip + cache-dependency-path: requirements.txt，粒度到文件 hash。
  4. cache playwright（actions/cache@v4） — 仅 RUN_UI=1 时命中（默认 RUN_UI=0 跳过，150 MB Chromium 下载浪费 runner）。
  5. 灌 DDL + seed（run） — mysql -h 127.0.0.1 -uroot -p$DB_PWD yami_shop < .github/workflows/yami_shop.sql + seed-data.sql（cart/order 硬编码 ID 用 seed，不依赖 fixture runner）。
  6. mvn 编译（run） — mvn -B -pl yami-shop-api -am package -DskipTests（-B 批模式 + -pl/-am 多模块聚合）。
  7. java -jar & 启服务（run） — nohup java -jar target/*.jar > app.log 2>&1 & + curl --retry 60 --retry-delay 1 --retry-connrefused http://localhost:8086/ 探活。
  8. pip install（run） — pip install -r requirements.txt（cryptography + pycryptodome 是 L12 §4.2 修过的 AES-ECB-PKCS7 依赖，缺包登录永远 A00005）。
  9. pytest + allure + upload（run + actions/upload-artifact@v4 + awesomecode/allure-action@v1） — pytest -m "not ui" --alluredir=./allure-results + allure generate + upload-artifact（30 天保存）+ allure-action 部署 gh-pages。

9 个 step 总耗时参考（ubuntu-latest，依赖已缓存）：灌 DDL 10 s + mvn 编译 3 min + 启服务 30 s + pip 30 s + pytest 2 min + allure 5 s = 约 6 分钟。首次跑（无缓存）会多 2-3 分钟（maven 依赖下载）。

4. 6 件非显然 fix 与降级

M2-D9-001 落地过程中踩到 6 个非显然 fix，全部沉淀在 doc/3-API接口/M2-D9-001-impl-notes.md：

  1. pytest skipif 顶层 load env — conftest.py 模块顶层调 _load_env() 注入 os.environ；CI 端用 env.PROD_ID 灌 .env，pytest collect 阶段（pytest.mark.skipif(os.getenv("PROD_ID")) 求值时）就不 skip。L11 §4.3 + L12 §4.3 都修过这个坑。
  2. AES-ECB cryptography 双装 — requirements.txt 显式装 cryptography + pycryptodome（缺包 common/mall4j_aes.py 报 ImportError → 登录永远 A00005）。
  3. cart/order 硬编码 ID 用 seed-data.sql — 不依赖 fixture runner 启动时插入；seed SQL 走 .github/workflows/seed-data.sql（INSERT INTO tz_order (order_id, ...) VALUES (...)），CI 灌完即可用。
  4. chromium 默认 RUN_UI=0 skip — 150 MB 下载浪费 runner 时间（PR 跑 6 min vs 4 min 差距），workflow_dispatch 手动开 RUN_UI=1 才装 playwright install chromium。
  5. allure-commandline 不在 pip — allure 是 Java 写的 CLI 工具，pip 装的是 allure-pytest 适配器；CI 用 awesomecode/allure-action@v1 一键 generate + deploy gh-pages，省 1 GB JDK 依赖下载。
  6. CI 网络不切镜像 — ubuntu-latest runner 国际链路本就快（GitHub 自家机房），切 tsinghua / aliyun 镜像反而慢；fallback 是本机原生启动（本机 docker mysql/redis + java -jar 跑 fat-jar，AGPLv3 边界 §6 已有路径）。

4.1 降级路径 3 条（CI 失败时立即套）

# 降级 1：跳过 allure gh-pages 部署（allure-action 失败时）
# allure-action 失败 = 不能部署报告，但 raw allure-results 仍可下载
- name: Upload raw allure-results
  if: always()  # 失败也上传，方便本地调试
  uses: actions/upload-artifact@v4
  with:
    name: allure-results
    path: test-cases/api-auto/allure-results
    retention-days: 30

# 降级 2：跳过 UI（chromium 下载失败 / 网络不通）
- name: pip install playwright
  if: env.RUN_UI == '1'  # 默认 0 直接跳过整个 step
- name: pytest UI
  if: env.RUN_UI == '1'
  run: pytest -m ui

# 降级 3：跳过 mvn 编译（已经 prebuild 时）
# 本地 mvn package 后把 fat-jar 上传成 artifact，CI 端 download
- uses: actions/download-artifact@v4
  with:
    name: yami-shop-api-jar
    path: yami-shop-api/target/
- name: skip mvn compile
  run: echo "using prebuilt jar"
CI 设计哲学
CI 不是"必须跑通"，是"跑不通也能拿到证据"。三件套：① raw allure-results（if: always() 上传，失败也能下载）；② services options --health-cmd（确认依赖真 ready，不是启了就连得上）；③ workflow_dispatch 手动 trigger（PR 失败时手动重跑，绕过 cron 限制）。

5. 思考题 + 下一课（M3-D10-001 Locust）

Q1：GitHub Actions runner 默认时区是 UTC 还是本地？答：UTC（date 命令 / allure report 时间戳全是 UTC，转换成北京时间 +8）。坑：seed-data.sql 里 created_at = NOW() 灌进去是 UTC，CI 调试时用 SELECT * FROM tz_order 看到时间差 8 小时别慌。

Q2：services block 启的 mysql:8.0.33 用什么机制确认 ready？答：--health-cmd="mysqladmin ping" + --health-interval=10s + --health-retries=10（10s 探一次，连探 10 次成功才算 ready，最长等 100 s）。坑：mysql 8 启动慢（要初始化 data dir），不加 health-cmd 会"启了但连不上"导致灌 DDL 失败。

Q3：awesomecode/allure-action@v1 部署 gh-pages 失败时，最简单的 fallback？答：改用 actions/upload-artifact@v4 上传 allure-report/ 目录（30 天保存），PR 评论附 Actions → Artifacts 下载链接，本地 allure open 就能看报告。代价：不能在线浏览趋势，但失败时这是最快恢复路径。
