3. 5 件产物速览：Collection + Env + 2 JS + 20 用例文档

来源：test-cases/postman/ 4 文件 + test-cases/api-20-cases.md 1 文件。本课的 5 件产物全部是纯文本，无二进制：

产物路径行数字节作用
Collection JSON test-cases/postman/mall4j-api-collection.json 1477 55 KB v2.1 schema；5 个 folder × 20 条用例；Pre-request + Tests 内联到每 item.exec
Environment JSON test-cases/postman/mall4j-api-environment.json 94 1.8 KB 17 个变量：base_url / token / prodId / addrId / ts / nonce 等
pre-request.js test-cases/postman/pre-request.js 22 974 B 通用 ts / nonce 注入（每请求前自动跑）
tests-snippet.js test-cases/postman/tests-snippet.js 22 841 B 通用断言 HTTP 200 + 业务码 200（每响应后自动跑）
20 用例文档 test-cases/api-20-cases.md 323 13 KB 每条用例的 ID / 路径 / method / 参数 / 期望 / 前置 / 步骤

关键设计：

  • snippet 内联到每个 item.exec（不是外链 --test-script）——Postman v2.1 schema不支持外链 JS 引用，每个 item 必须把 snippet 完整贴进 event.script.exec 数组。Newman CLI 才支持 --test-script 外链；UI 模式必须内联。
  • exclude PayNoticeController（@Hidden 注解）——PayNoticeController 在 Controller 上加了 @Hidden（Swagger 隐藏 + 对外不暴露），从 20 条用例里剔除，避免用例跑到 404 / 405。
  • Runner 顺序固定——5 个 folder 按"公开 → 认证 → 购物车 → 订单 → 异常"排列，Runner 按 folder 顺序执行，依赖关系天然成立（购物车依赖 token、订单依赖购物车）。

4. 核心概念 × 4（schema / env vs collectionVariables / AuthFilter / Runner 顺序）

4.1 概念 1：Postman v2.1 schema 结构

v2.1 schema 是 Postman 5 年稳定的 JSON 契约。顶层字段 = info + item（数组）+ 可选 event（Collection 级脚本）。每个 item = folder 或 request；递归结构：

    E --> G["script.exec[]

关键观察：

  • event[].script.exec 是字符串数组（不是单字符串）——每行一句，独立调试；这是 v2.1 schema 的设计取舍。
  • url 拆 raw / host / path / query 四块——{{base_url}} 模板写在 host 里；query 单独数组支持 key / value / disabled 三态。
  • item 可嵌套（folder 内嵌 folder）——本课用 1 层 folder，按业务模块切分。

4.2 概念 2：环境变量 vs 集合变量（collectionVariables）

Postman 变量作用域有 4 层：Global > Collection > Environment > Local。本课 5 件产物里只用到 Environment 和 Collection 两层：

变量作用域典型值谁设置
base_url Environment http://localhost:8086 人（启动前改一次）
username / password Environment testuser / test123456 人（凭据）
token Environment（运行时） 登录后写入 Tests snippet：pm.collectionVariables.set
ts / nonce / ts_short Collection（pm.collectionVariables） Date.now() / crypto.randomUUID() Pre-request snippet 自动注入

分工：人设的进 Environment（base_url、凭据）；机器跑的进 Collection Variables（ts、nonce、token）——人/机边界清晰。

// pre-request.js (22 行)
if (typeof pm !== 'undefined' && pm.collectionVariables) {
    pm.collectionVariables.set('ts', Date.now());
    pm.collectionVariables.set(
        'nonce',
        (typeof crypto !== 'undefined' && crypto.randomUUID)
            ? crypto.randomUUID()
            : String(Math.random()).slice(2)
    );
    var tsStr = String(Date.now());
    pm.collectionVariables.set('ts_short', tsStr.slice(-4));
}
作用域金句
base_url 用 Environment 是因为"开发 / 测试 / 生产"3 套 env 切换；ts 用 Collection 是因为它每请求都变，放 Environment 等于污染人设值。"人设的进 env，机器设的进 collection"——这条规则 5 件产物全遵守。

代码证据（ResourceServerAdapter.java:17-19）：

// 简化示意（实际从源码读出）
public final Predicate<ServerHttpRequest> AUTH_PREDICATE = request ->
    request.getURI().getPath().startsWith("/p/");

本课落地的 5 folder 对应关系：

folder路径前缀需 Authorization用例数
1.公开接口/prod/* /category/* /sku/* /indexImgs/* /search/*否8
2.登录/认证/login /login/sms /p/user/info登录无；info 需3
3.购物车/p/shopCart/*是3
4.订单/支付/p/order/* /p/pay/*是4
5.异常/边界混合按需2

关键洞察：/p/ 前缀是 mall4j 的"需要登录"信号；不带 /p/ 是公开 API。读源码 17-19 行比读文档更可靠——文档可能漏写这条规则。

4.4 概念 4：Runner 顺序与数据依赖

Collection 的 5 个 folder 在 Runner 里按 JSON 数组顺序执行（Postman Runner 的默认行为）。这个顺序不是任意的——它必须满足"token 提取 → token 复用"的依赖链：

// 2.登录/认证 folder 里的"登录获取token"用例，Tests snippet 里加 1 行：
if (typeof pm !== 'undefined' && pm.collectionVariables) {
    var body = pm.response.json();
    pm.collectionVariables.set('token', body.data.accessToken);
}

// 之后 3.购物车 / 4.订单 全部用例通过 {{token}} 模板取到 Bearer 注入

依赖图：

登录写入 token"]

反例：把"登录获取 token"放 folder 5，folder 3 / 4 会因为 token 为空跑出 401，20 条用例全红——这就是 Runner 顺序的工程价值。先无依赖、再有依赖是数据依赖型 Collection 的黄金法则。

面试金句
"Postman Collection Runner 默认按 item 数组顺序执行；依赖型用例（如登录 → 加购）必须按顺序排放，否则 token 取不到，后续用例全 401。数据依赖型 Collection 的黄金法则是'先无依赖、再有依赖'"——这句直接进 M1 项目经验。

5. 动手练：5 分钟把 8 条公开接口用例在 Runner 里跑过

学完概念后，5 分钟亲手跑一遍，这是 L09 的 win 产物——不需要后端启服务（公开 8 条不需要 token，Postman 点 Send 就能看到响应）。

  1. 任务 A：打开 Collection——把 test-cases/postman/mall4j-api-collection.json 拖进 Postman，左侧 Collections 面板应看到 5 个 folder：1.公开接口 / 2.登录/认证 / 3.购物车 / 4.订单/支付 / 5.异常/边界。截图 5 个 folder 列表存到 learning-records/0009-postman-folders.png。
  2. 任务 B：导入 Environment——把 mall4j-api-environment.json 导入 Postman → Environments → 选 mall4j-api-local；右上角环境切换器确认是绿色 active。把 base_url 改成本地 http://localhost:8086（或你启的后端端口）。
  3. 任务 C：跑 8 条公开接口——点 "1.公开接口" folder → Run → 选 folder → Run。Runner 报告应显示 8/8 passed（业务码 200）或 8/8 failed（如果后端没启）。无后端也至少能看见 Runner 报告结构（这就是资产化的意义）。
  4. 任务 D：改 Tests snippet——随便挑 1 条公开接口（如商品列表-分页查询）→ 点 Tests tab → 在 snippet 后加一行 pm.test('msg=SUCCESS', () => pm.expect(json.msg).to.eql('SUCCESS')); → Send → 看 Tests tab 第 3 条断言结果。
  5. 任务 E：导出 → Newman CLI（进阶）——把 Collection + Environment 导出回原目录；终端跑 newman run mall4j-api-collection.json -e mall4j-api-environment.json，看 20 条用例的报告（含 snipped 内联脚本）。

5.1 验证标准

  • ✅ 5 个 folder 列表截图清晰（folder 名称可见）
  • ✅ Runner 报告 8/8 通过（后端启）或 8/8 failed 但请求结构可见（后端未启）
  • ✅ 自己加的 msg=SUCCESS 断言在 Runner 报告可见
  • ✅ Newman CLI 跑出 20 条用例的报告（哪怕全红也行）
