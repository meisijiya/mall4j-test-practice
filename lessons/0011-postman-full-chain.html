关键设计：

  • 生成器优先于手改 JSON——v3.0 collection 是 30 KB Python 生成器的输出物；下次 ITEMS 列表调整后 python3 generate-collection-v3.py 一键重生,避免 PUT 行号漂移 / 字段缺失 / 多写少写。
  • snippet 内联到每个 item.exec（不是外链 --test-script）——Postman v2.1 schema不支持外链 JS 引用,每个 item 必须把 snippet 完整贴进 event.script.exec 数组。Newman CLI 才支持 --test-script 外链；UI 模式必须内联。
  • 探针 L3.1 + L3.2 必须在购物车前——Runner 按 folder 顺序执行,L3.1 写回 prodId → L3.2 用 prodId 查 skuList 写回 skuId → L3.3 加购用真实 prodId/skuId。

4. 核心概念 × 5（探针 / 5 业务码 / 写回双写 / 6 folder / 三种场景）

4.1 概念 1：探针请求机制（L3.1 + L3.2 修 D4 跨商品问题）

D4 v2.1 的致命伤：env 写死 prodId=18 / skuId=10,但这两个在 mall4j 数据库中不匹配（prodId=18 是"手机壳"商品,skuId=10 是"数据线"商品）→ 加购 L3.3 永远 FAIL → 链路 L4.1/L4.2/L5.1 全部 SKIP/FAIL。

D5 v3.0 的修法：在 collection 内置2 条探针（L3.1 + L3.2）而不是写 cart-fixture.sql：

    participant U as 测试用例
    participant E as Environment
    participant S as mall4j 后端

    S-->>U: {code:"00000", data:{prodId:1, prodName:"..."}}

pm.environment.set('skuId', 2)

探针核心代码（L3.1 写回 prodId）：

// L3.1 Tests snippet（内联到 event.script.exec）
if (typeof pm !== 'undefined' && pm.response) {
  try {
    var _j = pm.response.json();
    if (_j && _j.data && _j.data.prodId) {
      pm.collectionVariables.set('prodId', String(_j.data.prodId));
      if (pm.environment && pm.environment.set) {
        pm.environment.set('prodId', String(_j.data.prodId));
      }
      console.log('[M1-D5-001] prodId saved: ' + _j.data.prodId);
    }
  } catch(e) {
    console.log('[M1-D5-001] prodId extract skip: ' + e.message);
  }
}
探针金句
探针 = "用真实接口取代 fixture SQL"。零外部依赖 + 可重跑 + 降级友好（探针失败时降级到 env 默认值 prodId=1）。fixture SQL 仍可叠加：用户跑 evidence/cart-fixture.sql 后,env otherUserAddrId / orderNumberPaid 会被真实数据覆盖。

4.2 概念 2：5 业务码断言模板（T-A / T-B / T-D / T-E / T-F）

mall4j 后端 ServerResponseEntity 的 code 字段是 String 类型（不是 Integer）。D5 v3.0 全部断言统一为 String(j.code).to.eql('XXX')。5 模板覆盖 40 条用例：

模板业务码含义覆盖数JS 模板
T-A '00000' 成功 26 条 pm.expect(String(j.code)).to.eql('00000');
T-B 'A00001' 业务异常（账号密码错 / count=0 / basketIds 空） 3 条 pm.expect(String(j.code)).to.eql('A00001');
T-D 'A00014' @NotBlank 参数校验失败 2 条 pm.expect(String(j.code)).to.eql('A00014');
T-E 'A00005' 服务端异常（AES 解密失败 / 短信非手机号格式） 1 条 pm.expect(String(j.code)).to.eql('A00005');
T-F != '00000' 宽松（鉴权 401 / 短信默认关闭 / 状态机异常） 8 条 pm.expect(String(j.code)).to.not.eql('00000');

T-F 宽松断言示例（L6.1 未登录访问用户信息）：

// L6.1 Tests snippet
if (typeof pm !== 'undefined' && pm.test) {
  pm.test('HTTP 401 Unauthorized', function () {
    pm.response.to.have.status(401);
  });
  pm.test('业务码 != 00000', function () {
    var j = pm.response.json();
    pm.expect(String(j.code)).to.not.eql('00000');
  });
}
业务码金句
"业务码是字符串不是数字"——这是 mall4j 后端 ServerResponseEntity 的 Java 类型决定的。Postman 默认 pm.expect(j.code).to.eql(200) 永远 FAIL（"00000" ≠ 200）。显式 String(j.code) 转换是 D5 的铁律。

4.3 概念 3：写回 + 双写策略（basketId / orderNumber / addrId）

Newman 运行时,pm.response.json() 在 pre-request 和 test 阶段都能访问；但 header 引用 {{token}} 时,优先从 environment 读取（collectionVariables 在 header 解析前可能还没生效）。D4 v2.1 已踩坑：单写 pm.collectionVariables.set('token', ...),导致下游用例 header {{token}} 解析失败。

D5 v3.0 所有"写回"操作都是双写（collectionVariables + environment）：

sequenceDiagram
    participant T as Tests snippet
    participant CV as collectionVariables
    participant EV as environment
    participant H as 下游用例 header
    T->>CV: pm.collectionVariables.set('basketId', 123)
    T->>EV: pm.environment.set('basketId', 123)
    Note over CV,EV: 双写保证任意作用域都取得到
    H->>EV: 读 {{basketId}} 注入 header/body
    H->>CV: 备用（fallback）

L3.3 写回 basketId 代码：

// L3.3 Tests snippet（加购成功 → 写回 basketId）
if (typeof pm !== 'undefined' && pm.response) {
  try {
    var _j = pm.response.json();
    if (_j && _j.data && (_j.data.basketId || _j.data.id)) {
      var _v = _j.data.basketId || _j.data.id;
      pm.collectionVariables.set('basketId', String(_v));
      if (pm.environment && pm.environment.set) {
        pm.environment.set('basketId', String(_v));
      }
    }
  } catch(e) { console.log('[M1-D5-001] basketId extract skip'); }
}

3 个写回点的链路位置：

  • L3.3 加购成功 → 写回 basketId（Folder 3 内,L4.1 / L4.5 / L4.6 / L4.7 / L4.8 / L5.1 / L5.2 全部依赖）
  • L4.2 提交订单 → 写回 orderNumber（Folder 4 内,L4.5 / L4.6 / L4.7 / L4.8 全部依赖）
  • 登录 L2.1 → 写回 token（Folder 2 内,所有 /p/* 私有接口的 Authorization header 依赖）
双写金句
"Newman 解析 {{var}} 优先读 environment,其次 collectionVariables"——这是 Postman 沙箱的隐藏规则。单写 collectionVariables 在某些时序下会导致 header 注入失败（变量还未生效）。双写是 Newman 已知坑的标准解法。

5. 动手练：5 分钟迷你任务（任选 3）

学完概念后,5 分钟亲手跑一遍,这是 L11 的 win 产物——不需要后端启服务（公开 8 条 + 鉴权 5 条不需要 token 也能跑通或 FAIL 但请求结构可见）。

  1. 任务 A：打开 Collection v3.0——把 test-cases/postman/mall4j-api-collection.json 拖进 Postman,左侧 Collections 面板应看到 6 个 folder：1.公开接口 / 2.登录/认证 / 3.购物车 / 4.订单 / 5.支付 / 6.鉴权/异常/边界。截图 6 folder 列表存到 learning-records/0011-postman-folders.png。
  2. 任务 B：跑 Folder 1 公开 + Folder 2 登录 = 11 条——点 "1.公开接口" folder → Run → 选 folder → Run;同样跑 "2.登录/认证"。Runner 报告应显示 8/8 passed（业务码 00000）+ 3/3 passed（含 L2.3 短信 != 00000）或全 FAIL（如果后端没启）。无后端也至少能看见 Runner 报告结构。
  3. 任务 C：读探针 L3.1 + L3.2——展开 "3.购物车" → 点 "探针请求-取真实 prodId" → 点 Tests tab → 阅读写回 prodId 的 JS snippet → 理解 pm.collectionVariables.set + pm.environment.set 双写逻辑。
  4. 任务 D：跑 Newman CLI（进阶）——终端跑 NODE_PATH=$(npm root -g) newman run test-cases/postman/mall4j-api-collection.json -e test-cases/postman/mall4j-api-environment.json --reporters cli,html --reporter-html-export newman-report.html,看 40 条用例的报告（含 6 folder 分组 + 写回日志）。
  5. 任务 E：改业务码断言——随便挑 1 条 T-A 用例（如 L1.1 商品列表）→ 点 Tests tab → 把 to.eql('00000') 改成 to.eql('A00001') → Send → 看 Tests tab FAIL 行为。理解"断言错误是负向验证"。

5.1 验证标准

  • ✅ 6 folder 列表截图清晰（folder 名称 + 条数可见）
  • ✅ Runner 报告 8+3=11 条通过（后端启）或 11/11 failed 但请求结构可见（后端未启）
