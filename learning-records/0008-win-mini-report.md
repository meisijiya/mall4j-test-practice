## 1. 概述

### 1.1 模块背景
mall4j 登录注册模块覆盖用户端（`yami-shop-api` 端口 8086）账号生命周期：`/user/register` 注册入口 + `/user/login` 登录入口 + `/user/updatePwd` 改密入口 + `/user/info` 用户信息查询。鉴权链采用 Sa-Token + Spring Security 双层（详见 `yami-shop-security-admin`），密码使用 RSA 加密传输 + BCrypt 落库。
**Out-of-scope**：会员 / 权限模块（M1-D3-001 处理）、管理端用户管理（`yami-shop-admin` 模块）、短信验证码通道（仅 Mock）。**Out-of-scope 范围确认依据**：来源于 `CONTEXT.md §4 不测项速查` 与 `PROJECT_TARGET_BOOK.md §7 风险预案`——任何范围争议都要回溯到这两份源文档。
### 1.2 测试目标
- 验证 40 条用例在登录注册 4 类场景（正常注册 / 正常登录 / 异常登录 / 改密）下的功能正确性
- 验证鉴权链 4 类场景在登录注册模块的具体落地（无 token 调 `/user/info` / token 过期 / 跨用户改密 / 多角色菜单过滤）
- 暴露登录注册相关缺陷，按严重等级归档
- 形成一份 5 章精简版测试报告，作为 M1-D3-001 完整 9 章报告的样本

### 1.3 测试范围
**In-scope**：登录注册 40 条用例（等价类 18 / 边界值 14 / 场景法 8）
**Out-of-scope**：会员 / 权限模块（M1-D3-001 处理）、管理端用户管理（`yami-shop-admin` 模块）、短信验证码通道（仅 Mock）。

## 4. 结果分析（三流合一视角）

### 4.1 主链路第一步：登录通过情况

登录是三流合一 6 步主链路（登录 → 加购 → 下单 → 支付 → 收货 → 评价）的**资金流起点**——只有登录成功拿到 token 后，token 才能作为后续 5 步请求的鉴权凭证。

| 步骤 | 用例编号 | 三流归属 | 通过 | 备注 |
|---|---|---|---|---|
| 1. 登录 | LOGIN-001 | 资金流起点（拿 token） | (待回填) | 主链路能否继续的唯一闸口 |

### 4.2 鉴权链通过情况（4 类）

| 场景 | 用例覆盖 | 通过 | 备注 |
|---|---|---|---|
| 不带 token 调 `/user/info` → 401 | AUTH-001 | (待回填) | 最低门槛 |
| token 过期 → 401 | AUTH-002 | (待回填) | 需清 Redis 缓存 |
| 跨用户改密 → 403 | UPD-005 | (待回填) | 对应 BUG-002 改密未鉴权 |
| 多角色用户登录 → 按角色-菜单过滤 | AUTH-003 | (待回填) | RBAC |

### 4.3 关键发现（待回填）

- 主链路起点判断：(待回填)——LOGIN-001 通过/失败将决定整个 6 步主链路测试能否启动
- 鉴权链判断：(待回填)——BUG-002 复现成功则阻塞整个登录注册模块发布
- 改密功能判断：(待回填)——BUG-003 复现成功则改密功能必须从 P0 降为 P2

## 5. 结论

### 5.1 是否达到发布标准（登录注册模块）

判定规则（来自第 8 课 §8.1）：

- 通过率 ≥ 95% 且 Critical 全部修复 → **建议发布**
- 通过率 85%-95% 或存在 Major 未修复 → **有条件发布**
- 通过率 < 85% 或存在 Critical 未修复 → **不建议发布**

**当前建议（待回填）**：基于上述规则的实际数字，登录注册模块作为三流合一主链路第 1 步（资金流起点），其发布门槛应**高于普通业务模块**——除常规 95% 通过率口径外，还需满足鉴权链 4 类场景（无 token / token 过期 / 跨用户改密 / 多角色菜单）全绿、bug-list.md BUG-002（改密未鉴权 Critical）必须修复并复测通过。这是 §7.3 阻塞发布问题的硬约束，不可让渡。

1. **优先复现 BUG-002 / BUG-001 / BUG-003** 这 3 条登录注册相关 Critical/Major 缺陷——复现成功才能确认 bug-list.md 静态分析的准确性
2. **回归测试范围**：修复后回归登录注册 P0 全部 12 条 + P1 关键 5 条
