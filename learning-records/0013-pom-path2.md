- **POM 7 Page 类继承链 + 职责分工（核心 fix #1）**：`ui_pages.py` 从 D7 的 91 行扩到 479 行，新增 `LoginPage / HomePage / ProdListPage / ProdDetailPage / CartPage / OrderPage / UserPage` 6 个 Page 类（BasePage 是 D7 已交付的父类）。每个 Page 类只管自己页面的 selector + 业务方法 —— `LoginPage` 管 fill_form / click_submit / wait_for_login；`CartPage` 管 check_all / update_count / checkout / count_items；`OrderPage` 管 cancel_order / click_pay / click_detail（按 index 选行）。详见 `test-cases/api-auto/common/ui_pages.py:116-165`（LoginPage）+ `:283-311`（ProdListPage）+ `:317-345`（ProdDetailPage）+ `:351-389`（CartPage）+ `:395-432`（OrderPage）+ `:438-466`（UserPage）—— 这是"测试工程师的核心抽象能力：把页面操作收敛到 Page 类、用例只调方法不碰 selector"。

## 含义（用户能向面试官讲清楚什么）
- "为什么 D8 要做 POM 完整化（7 个 Page 类）而不是 D7 的 BasePage 单类就够了"：D7 起步阶段只有 `LoginPage` 和 1 个 `BasePage`，UI 测试广度只 2 条 —— BasePage 已经能 cover。D8 扩到 8 条 UI 用例 + 商品列表 / 商品详情 / 购物车 / 订单 / 用户中心 5 个新页面，每个页面有自己独特的 selector 和业务方法（购物车的 check_all / update_count / checkout，订单的 cancel_order / click_pay）—— 这些 selector 和方法分散到 BasePage 会让父类臃肿、selector 重名冲突。POM 完整化让每个 Page 类管自己的 selector 字典 + 业务方法，用例只调 `cart_page.check_all()` 不碰 `.item-check` selector —— 这是"Page Object 模式的核心价值：把 UI 自动化按页面维度解耦，每个页面一个类、selector 内聚、用例调方法不碰 selector"。
- "为什么 LoginPage 的 selectors 要做成双 key dict（shop / admin）而不是两个独立类 LoginPageShop / LoginPageAdmin"：两个独立类会导致 selector 和方法大量重复（fill_form / click_submit / wait_for_login 三套方法都重复）—— DRY 违反。双 key dict + 按 port 参数切换 selector 让代码量减半，且新增第三端（如 mini-program）只需加 dict key + port 分支，不改方法签名。这是"测试代码的复用设计：dict 多态 vs 类继承"。面试时讲清"为什么我没继承 AdminLoginPage(LoginPage) 而是用 dict 多态"展示 OOP 设计权衡能力。
- "为什么 mock_captcha_route 必须在 page.goto 之前注册（而不是之后）"：playwright 的 `page.route(pattern, handler)` 是在 chromium DevTools Protocol 层注册网络拦截 hook，**hook 注册时机决定能否拦截**。`page.goto(url)` 触发浏览器导航后立即发请求 —— 如果 hook 还没注册，请求就走真实网络；hook 注册后只对**后续**请求生效。所以 `mock_login_response(page)` 必须在用例**第一步**调用，docstring 显式标注 "**必须在 page.goto 之前注册**"。这是"测试代码时序约束的硬知识" —— 不知道这点的工程师会把 mock 写在用例最后，结果断言永远看到真实响应。面试时可讲清"playwright route 是注册时机敏感 + DevTools Protocol 层的网络拦截"。
- "为什么前端 mock 的是 `/adminLogin` 而不是 `/login`"：mall4v 前端 `views/common/login/index.vue:118-127` 的 `http.post('/adminLogin', ...)` —— 即使是普通用户登录（`sys_type='ORDINARY'`），前端代码也走 `/adminLogin` 端点（不是 `/login`）。`/login` 是另一套历史遗留端点（admin 后台可能用或 mobile 端用）。所以 `mock_login_response` 同时注册 `**/adminLogin + **/login` 两个 glob pattern —— 即使前端切到 /login 端点也能 mock 命中。这是"前端源码阅读决定测试 mock 端点的硬约束" —— 没读前端源码就 mock 的工程师会把端点写错，导致登录按钮点了走真实后端 → 401 / captcha 校验失败。面试时可讲清"为什么我 mock /adminLogin 而不是 /login —— 因为我读了 mall4v login/index.vue 第 118-127 行"。
- "为什么 admin 后台用 Element Plus selector 而 shop 商城用 mall4v 自有 selector"：yami-shop-admin 项目是独立的前端（Vue 3 + Element Plus 2.x），placeholder 文案带"请"字（`请输入用户名` / `请输入密码`），按钮是 `el-button--primary`；shop 端 mall4v 是自有 Vue 组件库 + Vant 风格，placeholder 是"账号" / "密码"，按钮是 `.login-btn`。两套前端两套 selector 是历史决定的（admin 端独立团队 + Element Plus 是后台标准）—— 测试工程师写 selector 时必须 grep 前端 vue 文件确认 placeholder 文案，**不能假设 selector 命名约定跨前端统一**。这是"前端多技术栈带来的 selector 复杂度" —— 真实项目的 UI 自动化经常面对 2-3 套前端，测试要按前端分别写 selector。
- "为什么 allure severity 在缺包时优雅降级 + pytest marker 双层"：allure 报告是锦上添花（allure-pytest 没装也能跑 pytest），但 pytest marker 是 pytest 自己的机制（`-m severity` 必须注册否则报 unknown marker）。双层设计：`@pytest.mark.severity("critical")` 是纯 pytest marker 不依赖 allure（即便没装 allure-pytest 也能跑）；`@allure.severity(...)` 是 allure 装饰器（没装 allure 时降级为 noop）。两套机制独立运行、互不依赖。这是"测试报告工具的兼容层设计" —— agent 在不同环境（装了 allure / 没装 allure）都能交付，allure_compat.py 是关键兼容层。面试时可讲清"为什么我的测试框架装了 allure / 没装 allure 都能跑"。
- "为什么 D8 UI 用例按 controller 维度扩展（8 条不是 30 条）"：UI 自动化的 ROI 比接口自动化低 —— 写 UI 用例要处理 selector 维护 + 浏览器兼容性 + mock captcha + 截图存证，每条用例成本是接口用例的 3-5 倍。D8 只在最有 ROI 的 5 个 controller 写 UI 用例（Login / Prod / Cart / User / Order），其他 17 个 controller 只做接口覆盖（Path 1 路径 + mock_route）。8 条 UI + 75 接口 = 83 条总用例 —— 这是"测试金字塔的工程现实"：UI 自动化少而精、接口自动化多而广。面试时可讲清"为什么我没把 UI 用例堆到 30 条 —— ROI 不划算"。
- "为什么 D8 路径 2 mock captcha 是 D7 路径 1 的迭代升级而不是替代"：D7 路径 1 调 `/adminLogin` API 拿 token + `page.context.add_cookies` 注入 + `page.goto` 验证路由 —— 验证的是"前端能正确读 cookie 并跳页"，不验证表单填写流程。D8 路径 2 加 `page.route` mock captcha + 真填表单 —— 验证的是"用户完整登录链路"（输入用户名密码 + 点登录 + 路由跳转）。两个路径互补：路径 1 跑得快（无浏览器渲染）、路径 2 跑得慢但更接近真实用户行为。测试工程师的工程权衡是"路径 1 跑冒烟、路径 2 跑深度" —— 这是"测试设计的多层次验证"。
- "为什么 mock_route 设计为 fixture 工厂模式而不是静态方法"：fixture 接受依赖注入（conftest 自动注入 `page`），用例只传 url_pattern + response_body；静态方法要用例自己 `from common.ui_pages import MockRoute; MockRoute.mock(page, ...)`，且如果 mock_route 内部要读 conftest 配置（如全局 captcha mock token）就麻烦。fixture 是 pytest 的依赖注入标准范式，可与 `@pytest.fixture(autouse=True)` 联动自动应用到所有用例。这是"测试代码的依赖注入设计" —— fixture 让 mock_route 可测试、可 mock、可配置。
- "为什么 D8 是 M2-D7-001 的合流扩展而不是另起炉灶"：D7 已交付 pytest YAML + 路径 1 UI 框架（49 用例 + 2 UI）；D8 不是"重写 D7"也不是"D7 翻译"，而是"在 D7 框架基础上扩 POM 完整化 + 路径 2 mock + allure severity + 接口用例从 47 扩到 75"——保留 D7 的 yaml_loader / BasePage / conftest fixture / api wrapper 风格全部复用，只新增 7 Page 类 + 12 yaml + 12 wrapper + 6 UI 用例 + allure_compat 4 函数。这是"框架演进的合流思维" —— 不重写、只扩展、保留已有接口的向后兼容。面试时可讲清"为什么 D8 是演进不是重写"。
- "为什么 D8 上 allure severity 而不是另起一个 severity 框架"：severity 分级是 allure 报告标准件（allure.severity_level.BLOCKER/CRITICAL/NORMAL/MINOR/TRIVIAL 五级），CI 集成 allure 报告后可直接按 severity 过滤用例（`--allure-severities normal,critical`）。另起框架要自己写报告渲染器 + CI 解析 + 邮件分拣 —— ROI 不划算。复用 allure 标准件 + `allure_compat.py` 优雅降级让"装了 allure 出报告 / 没装 allure 跑 pytest" 都行。这是"测试报告标准件复用 vs 自研框架"的工程权衡 —— 面试时可讲清"为什么我选 allure 而不是自研 severity 框架"。
