## 本节收获
- **test_prod.py 3 处 bug 修复的故事（D5 同坑二次踩）**：D6 `test_prod_info` / `test_page_prod` / `test_get_sku_list` 三条用例曾断言 `assert_business_code(resp, 200)` — 200 是 HTTP 状态码，mall4j 业务码字段是 `String`（`'00000'` / `'A00014'`），整数 200 永远 FAIL。D7 改 `assert_business_code(resp, expected_code)`（`expected_code` 来自 yaml 字符串字段），三处断言现在与 yaml `expected_code` 严格一致 — 详见 `test-cases/api-auto/testcases/test_prod.py:47` / `:61` / `:117`。这是 D5 Postman v3.0 "5 业务码断言模板"的 pytest 侧等价坑。
- **yaml substitute + SafeDict 模板替换机制**：D5 Postman `{{var}}` 在 Newman 里由 collectionVariables + environment 双写解析；pytest 侧没有 Newman 那套作用域，由 `yaml_loader.substitute(value, mapping)` 递归替换 dict / list / str 里的 `{{var}}` 占位，`SafeDict.__missing__` 返回 `"{{key}}"` 字面避免 KeyError（缺 key 不崩，调试时可看到未替换变量名）。详见 `test-cases/api-auto/common/yaml_loader.py:38-63` — 18 行核心代码（`SafeDict` + `substitute`）。
- **probe_sku / probe_addr / probe_order 三种探针 helper**：与 D5 Postman v3.0 Folder 3 探针 item 同源思路 — 先调 `/prod/prodInfo?prodId=1` + `/sku/getSkuList?prodId=1` 拿真实 skuId（或 `/p/address/list` 拿 addrId / `/p/myOrder/myOrder` 拿 orderNumber），写回 `os.environ` 供 yaml `{{skuId}}` / `{{addrId}}` / `{{orderNumber}}` 替换。详见 `test-cases/api-auto/common/yaml_loader.py:105-192` — 三个探针函数 + 一个 `write_env(key, value)` helper。
- **Playwright 路径 1：API 拿 token + cookie 注入绕开滑块 + AES**：D7 UI 起步只引入 2 条用例（admin + shop），不碰滑块验证码。`test_admin_login` 调 `/adminLogin`（带 AES 加密密码）拿 accessToken → `BasePage.inject_auth_cookie(token, base_url)` 注入 Sa-Token `Authorization` cookie → `page.goto(admin_url + "/")` + `wait_for_url("/home")` 验证路由跳转 + `screenshot("ui-evidence/test_admin_login.png")` 存证。详见 `test-cases/api-auto/common/ui_pages.py:257-267`（`inject_auth_cookie`） + `test-cases/api-auto/testcases/test_ui_login.py:117-130`（admin 用例）— 完全等价于前端 `cookie.set('Authorization', token)`。
- **conftest.py 缺包优雅降级（顶层 try/except + 双层 skip）**：用户没装 playwright 时，`from playwright.sync_api import sync_playwright` 在 conftest 模块顶层 try/except ImportError — `_HAS_PLAYWRIGHT = False` 时 `_playwright_browser` fixture 直接 `pytest.skip("Playwright 未安装；UI 用例跳过。")`；UI 用例自身再加 `@pytest.mark.skipif(not os.getenv("RUN_UI"))` 兜底（默认 skip；用户跑 `RUN_UI=1 pytest -m ui` 才启）。双层 skip 效果：未装 playwright + 未设 RUN_UI 时 collect-only 仍 PASS，UI 用例标 skip 不影响接口用例。详见 `test-cases/api-auto/conftest.py:142-175`（顶层 try + browser fixture）。
- **pytest marker 双层定义（`pytest.ini` + 装饰器）**：D7 `pytest.ini` 加 `markers = ui: UI 自动化用例（需 chromium）`，`test_ui_login.py` 顶层类标 `@pytest.mark.ui`；跑 UI 用例命令 `pytest -m ui`（默认全跑接口），跑接口用例 `pytest -m "not ui"`（默认排除 UI）。详见 `test-cases/api-auto/pytest.ini:13-18` + `test-cases/api-auto/testcases/test_ui_login.py:284-288` — 5 行 marker 配置。

## 含义（用户能向面试官讲清楚什么）
- "为什么 D7 用 YAML 数据驱动而不用 @pytest.mark.parametrize 手写参数"：手写参数把测试数据和测试逻辑耦合在一个文件里 — 加一条用例要改 .py、加两条要复制粘贴两份几乎相同的函数。YAML 把数据外置，测试函数变成模板（`def test_xxx(self, case, api_client)`），加用例只改 yaml 不改 .py — 测试广度从 10 扩展到 49 是 5 倍，但代码改动只在 yaml 文件。这是"测试工程师的核心能力：用数据驱动把测试用例的扩展性从代码层提到数据层"。
- "为什么 `{{skuId}}` 模板替换用 SafeDict 而不是 f-string 或 str.format"：f-string 是 Python 字面替换，遇到 dict / list 嵌套就崩（`skuId` 经常嵌在 `body: { prodId: 1, skuId: '{{skuId}}' }` 这种深层结构里）；str.format 也只替换 str 不递归 dict。`substitute(value, mapping)` 递归遍历 dict / list / str，遇到 str 调 `str.format_map(SafeDict(mapping))` — `SafeDict.__missing__` 缺 key 返回 `"{{key}}"` 字面而不是 KeyError，让"未替换占位"在测试日志里可见（断言 `prodId == 1` 失败时立刻能看到 `skuId == '{{skuId}}'` 而非崩溃）。这是"Python 模板替换正确写法 vs 常见错误写法"的典型例子。
- "为什么 yaml 探针是 D5 Postman v3.0 探针在 pytest 侧的等价物"：两边都面对同一个问题 — 硬编码 `prodId=18/skuId=10` 跨商品导致 FAIL。D5 修法：Folder 3 头部加探针 item + Tests 脚本 `pm.collectionVariables.set + pm.environment.set` 双写回 env，下游 `{{skuId}}` 引用；D7 修法：`probe_sku(api_client, prod_id=1)` 函数内部调 `/prod/prodInfo` + `/sku/getSkuList` 拿真实 ID + `os.environ['skuId'] = str(sku_id)` 写回，下游 yaml `{{skuId}}` 在 parametrize 阶段 substitute 替换。机制相似但 API 不同（Postman 是 collection 顺序约束，pytest 是 fixture 函数调用），这是"测试设计模式在不同框架的同构映射" — 面试时可讲清"为什么我没重复造轮子，而是把 Postman 的好思路迁移到 pytest"。
- "为什么 UI 路径 1 用 API 拿 token + cookie 注入而不是真填表单"：UI 自动化起步阶段真填表单要解 3 个难题 — ① mall4j 前端 AES 加密密码（Python 端要复刻 ECB + Pkcs7）② 滑块验证码（OCR / 第三方打码 / mock）③ Sa-Token 鉴权 cookie 时序。路径 1 直接绕开：API 调 `/login` 拿 token → `page.context.add_cookies` 注入 → `page.goto` 验证路由 — UI 测试变成"cookie 注入 + 路由跳转 + 截图存证"的纯前端集成验证。这是"测试 ROI 权衡"：D7 只验证"前端能正确读 cookie 并跳页"，D8 才上路径 2 mock captcha + 真实填表单；先有路径 1 让 UI 框架跑通，再迭代路径 2 加深度 — 避免起步阶段被滑块卡死。
- "为什么 conftest 顶层 try/except ImportError 是 collect-only 通过的关键"：`pytest --collect-only` 不执行 fixture 函数体，但**会执行模块顶层 import**。如果 conftest 顶层 `from playwright.sync_api import sync_playwright` 在没装 playwright 的环境下直接 ImportError，conftest 加载失败 → 整个 test session 的 collect 全挂 — 接口用例都收不到。`try/except ImportError: _HAS_PLAYWRIGHT = False` 让顶层 import 永远不抛错；fixture 函数体里再 `if not _HAS_PLAYWRIGHT: pytest.skip(...)` 做运行时兜底。这是"agent 在缺包环境交付 pytest 框架的标准范式" — 不光是 playwright，allure-pytest / pytest-playwright / xdist 都用同样套路。
- "为什么 pytest marker 要双层定义（pytest.ini + 装饰器）"：单在装饰器写 `@pytest.mark.ui` 跑 `pytest -m ui` 会报 `PytestUnknownMarkWarning`；单在 pytest.ini 写 markers 不写装饰器，pytest 不知道哪个用例属于 ui 类。双层定义让 `pytest -m ui`（跑 UI）/ `pytest -m "not ui"`（跑接口，排除 UI）/ `pytest`（全跑，UI 默认 skip）三种命令都合法。这是 pytest marker 的最小可用模式，agent 写框架必加。
- "为什么 49 条用例分三场景算 PASS（不是含糊而是诚实）"：黄金路径（启 8086 + 注 fixture + 启 admin 8085）≥ 38 PASS / 降级路径（仅探针，无 fixture）30+ PASS / 失败路径（8086 未启）0 PASS 但鉴权 5 条靠 HTTP 401 仍能跑。写简历时强调"骨架 PASS + 业务链路依赖前置数据 ready" — 这是"测试工程师的诚实判定"：不写"全部通过"也不写"全部失败"，而是用场景分级告诉读者"什么条件下能跑多少" — 这是大厂面试官最看重的工程现实主义。
- "为什么 D7 是 M2-D6 + M1-D5 的合流升级而不是另起炉灶"：M2-D6-001 已交付 pytest + 10 用例骨架（含 AES 加密 / 业务码断言 / BCrypt 前缀 / token 作用域 4 个 fix），M1-D5-001 已交付 Postman v3.0 完整链路 + 探针机制；D7 不是"D6 重写"也不是"D5 翻译"，而是把两者最佳实践合并：数据驱动模式（YAML 来自 D5 探针风格）+ 接口框架（D6 pytest + ApiClient + assertion）+ UI 起步（新领域）= M2-D7-001。面试时讲清"为什么 D7 是合流不是重写"展示架构演进能力。
- "为什么 D7 不上 UI 路径 2（mock captcha）"：D7 时间盒只够交付"框架起步" — 加 mock captcha 要做 3 件事：① `page.route("**/adminLogin", lambda r: r.fulfill(...))` 拦截后端点 ② `page.route("**/captcha/**", lambda r: r.fulfill(status=200, body='{}'))` mock 响应 ③ 真实填表单（userName / password / 拖动滑块坐标）— 这些是 D8 的迭代目标。D7 只交付"路径 1 让 UI 框架跑通 + 截图存证"，D8 才在路径 1 基础上加路径 2 mock。**这是"v1/v2 分阶段交付"的工程思维** — 大厂不喜欢"大而全"的设计，喜欢"小步快跑 + 留好扩展点"的演进能力。
