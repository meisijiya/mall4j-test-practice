2. 鉴权（Sa-Token）四必测速查表

来源：doc/4-技术实现/1-权限体系.md。每个接口测试都必须先过这四道关。

编号场景期望触发代码入口
A1不带 token 调任意需要登录的接口401 / UNAUTHORIZEDSa-Token 拦截器 → AuthUtil.getToken() 为空
A2带过期 token 调接口401 / TOKEN_EXPIREDSa-Token 拦截器 → Token timeout 异常
A3普通用户访问 admin 接口403 / FORBIDDEN@PreAuthorize("@pms.hasPermission(...)") 不匹配
A4多角色用户登录（如运营 + 客服）按 tz_sys_menu 的 role_id 取并集返回菜单GET /sys/menu/nav 返回 menuList

反模式警告：只测 A1 就声称"鉴权测过了"——A3（垂直越权，OWASP Top 10）和 A4（菜单越权）才是线上最常爆雷的点。

测试归属：conftest.py 造 4 个 fixture（no_token / expired_token / user_token / admin_token），每个接口测试至少覆盖 A1+A3。

3. 幂等三必测速查表（订单 / 支付 / 退款）

来源：CONTEXT.md 第 37-40 行 + 第 2 课支付幂等三道关。资金流接口每一个都必须测幂等。

编号场景期望代码入口
I1同一 orderNumber 重复点"提交订单"仅成功一次，第二次返回"订单已存在"OrderController.submitOrders → ConfirmOrderCache + tz_order 唯一索引
I2同一 payNo 多次到达仅更新一次订单状态，后续回调幂等返回PayNoticeController + OrderSettlementMapper.updateToPay() 乐观锁 version+1
I3同一 refundNo 多次提交仅退一次，tz_order_refund.return_money_sts 不重复置 1RefundController.applyRefund → tz_order_refund 唯一索引

反模式：只测"正常下单一次能成功"——这是单点通过，幂等路径完全没覆盖。

4. 分布式锁（Redisson）三必测速查表

来源：doc/4-技术实现/7-分布式锁.md。mall4j 提供 @RedisLock 注解（基于 Redisson），但当前开源版业务代码里暂未发现实际使用点。即使没启用，测试用例仍要预留场景。

编号场景期望失败模式
L1同一商品 100 并发扣减库存（库存预置 50）最终库存 = -50 之前的 0，成功订单 = 50，不超卖没加锁 → 100 个请求都看到 stock=50 → 超卖 50 个
L2同一订单号 50 并发提交仅成功 1 次，其余返回"重复提交"没加锁 → 同一订单被扣 2 次款
L3锁过期时间边界：业务执行 4.9s锁未失效，第二个请求被阻塞锁过早释放 → 第二个请求抢到锁 → 并发问题

锁机制三要素：key=redisson_lock:{lockName}:{SpEL解析结果}，默认过期 5000ms，注解 @RedisLock(lockName="stock", key="#prodId")。

面试金句：Redis 分布式锁不是银弹，超时时间 + 业务执行时长必须配对；业务超 5 秒必须显式指定 expire。

5. 参数校验（Jakarta Validation）四必测速查表

来源：doc/4-技术实现/3-参数校验.md。用 @Valid + @NotNull / @NotBlank 做参数校验，校验失败统一进 ServerResponseEntity.fail(...)。每个接口都至少 4 条参数校验用例。

编号场景期望示例
V1必填字段缺失4xx + PARAM_MISSING提交订单时不传 userAddrId
V2字段类型错误4xx + PARAM_TYPE_ERRORprice 字段传字符串 "abc"
V3字段长度超限4xx + PARAM_LENGTH_OVER商品名称传 1000 字符（限 200）
V4枚举值非法4xx + PARAM_INVALID订单状态传 status=99（仅 1-6 合法）

测试设计要点：每个字段一条用例（字段粒度）；边界值优先（必填字段 → 缺失/空串/null/空格；长度字段 → min-1/min/max/max+1）；错误信息 msg 必须包含"哪个字段错了"。

反模式：前端做校验就以为后端不用管——前端校验可绕过（curl / Postman / 自动化脚本），后端 @Valid 才是最后一道防线。

6. 分页边界（MyBatis-Plus PageParam）六必测速查表

来源：doc/4-技术实现/4-分页实现.md。基于 MyBatis-Plus PageParam<T>，默认 current=1 / size=10，size 最大限制 = 100。所有分页接口都至少 6 条边界用例。

编号入参期望验证点
P1current=0兜底为 1 或返回 400MyBatis-Plus 是否 current < 1 自动修正
P2current=-1返回 400（非法参数）Jakarta Validation @Min(1) 是否生效
P3size=0兜底为 10 或返回 400默认值兜底逻辑
P4size=99999兜底为 100 或返回 400size > 100 截断逻辑
P5总记录数 = 0返回空列表 + total=0空数据路径
P6总记录数 = 1total=1 + records.length=1 + 分页器显示 1 页单数据路径

复杂关联分页陷阱：订单明细分页（OrderServiceImpl.pageOrdersDetailByOrderParam()）是手写 SQL + 单独 count SQL，join 后行数 ≠ 订单数。total 应等于订单数而非订单项数，records.size 可能 > PageParam.size（一订单多行）。

反模式：只测 current=1&size=10（默认参数）就声称"分页测过了"——P1-P4 一旦有 Bug 就是 P0 事故。

7. 反模式速查表（不要孤立测"点"）

来源：CONTEXT.md 第 15 行——mall4j 要测"流"，不要测"点"，孤立用例不写进用例库。

反模式（孤立测点）为什么错正确做法（全链路）
"商品列表能加载"单点通过，订单全流程可能挂加载 → 加购 → 下单 → 支付
"登录接口返回 200"只验状态码，没验 token 有效性登录 → 拿 token → 调 /sys/menu/nav 验真能用
"支付回调能调通"没验幂等，没验金额来源回调 → 验签 → 幂等 → DB 更新 → 二次回调幂等返回
"退款能成功"没验原路返回（微信单退到支付宝）退款 → 查 tz_order.pay_type → 验退款渠道匹配

判断标准：这条用例单独跑通 ≠ 业务能跑通。必须把"点"串成"流"才能进用例库。

每个模块新功能上线前，按这个矩阵逐项打钩——至少把"功能 + 接口 + 异常"三列打钩。
